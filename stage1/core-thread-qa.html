코어 · 스레드 · 스케줄링 질문 정리

물리 · 논리 코어와 프로세스 · 스레드는 어떤 관계인지, 서버 CPU는 코어당 스레드가 몇 개인지, STT 채널은 코어와 어떻게 연결되는지, CPU 스케줄링이 실무에서 왜 중요한지 등 질문 9개를 그림 3장으로 정리 · STAGE 1 운영체제 · 2026-11-12

Q1.물리 코어, 가상 코어와 프로세스, 스레드는 어떤 관계인가?

두 층으로 나눠 보면 된다. 물리 코어 · 논리 코어는 하드웨어, 프로세스 · 스레드는 소프트웨어(OS)이고, 둘을 잇는 것이 스케줄러다.

  • 물리 코어: 실제로 명령을 처리하는 회로. 연산 장치(ALU · FPU)와 L1 · L2 캐시를 가진다
  • 논리 코어(가상 코어): SMT(인텔은 하이퍼스레딩)로 물리 코어 하나를 OS에 2개처럼 보이게 한 것. 실행 상태(레지스터)만 2벌이고 연산 장치는 1벌을 나눠 쓴다. 8코어 16스레드 CPU면 OS는 CPU가 16개라고 본다
  • 프로세스: 실행 중인 프로그램이자 메모리 · 파일 · 소켓 같은 자원을 담는 그릇
  • 스레드: 프로세스 안의 실행 흐름. CPU에 올라가는 실제 단위는 프로세스가 아니라 스레드다

그래서 한 순간에 동시에 실행되는 스레드 수는 논리 코어 수와 같다. 스레드가 그보다 많으면 스케줄러가 몇 ms 단위로 번갈아 실행(시분할)하고, 바꿀 때마다 문맥 교환 비용이 든다. 스레드가 1개인 프로세스는 코어가 아무리 많아도 코어 1개만 쓴다.

그림 1. 스레드 6개를 스케줄러가 논리 코어 4개에 번갈아 올린다. 논리 코어 둘은 물리 코어 하나의 연산 장치를 나눠 쓴다

Q2.서버에서는 물리 코어 1개에 가상 코어 2개밖에 안 되나?

아니다. 코어당 2개는 x86 서버(인텔 Xeon · AMD EPYC)에서 가장 흔한 구성일 뿐이다.

  • 코어당 1개: ARM 서버(Ampere Altra · AWS Graviton). SMT 없이 물리 코어를 많이 넣는 방향
  • 코어당 2개: x86 서버 대부분
  • 코어당 4~8개: IBM POWER(SMT4 · SMT8), Oracle SPARC. 연산 장치를 넓게 설계해서 여러 스레드가 나눠 써도 효과가 난다

x86이 2개에서 멈춘 이유는, 연산 장치 하나를 셋 이상이 나눠 쓰면 서로 다투느라 손해가 커지기 쉬워서다. 같은 CPU라도 BIOS나 OS에서 SMT를 끄면 코어당 1개로 보이고(사이드채널 보안 대응으로 끄기도 한다), VM이라면 OS가 보는 CPU는 vCPU다. 클라우드의 vCPU 1개는 보통 하이퍼스레드 1개(물리 코어의 절반)다.

lscpu | grep -E "^CPU\(s\)|Thread|Core|Socket|Hypervisor"
cat /sys/devices/system/cpu/smt/control   # on / off / notsupported

Q3.CPU의 스레드는 코어의 자원을, 프로세스의 스레드는 프로세스의 자원을 나눠 쓰는 건가?

맞다. 이름만 둘 다 스레드일 뿐 다른 층의 개념인데, 실행 상태는 각자 갖고 큰 자원은 공유한다는 구조가 같다.

  • CPU 스레드(논리 코어): 각자 = 레지스터 · 실행 위치(PC) / 공유 = 연산 장치 · L1 · L2 캐시
  • 프로세스의 스레드: 각자 = 스택 · 레지스터 값 · 실행 위치 / 공유 = 힙 · 전역 변수 · 열린 파일 · 소켓

다만 프로세스가 가진 자원에 CPU 시간은 들어가지 않는다. CPU 시간은 스레드 하나하나가 직접 배정받기 때문에, 스레드 10개짜리 프로세스는 1개짜리보다 CPU를 더 많이 가져갈 수 있다(cgroup으로 묶어서 제한하지 않는 한). 정리하면 CPU 스레드는 실행 자리, 프로세스의 스레드는 실행할 일이고, 스케줄러가 일을 자리에 앉힌다.

Q4.한 프로세스의 스레드들이 각각 다른 코어에서 실행될 수 있나?

된다. 같은 프로세스의 스레드들이 서로 다른 코어에서 진짜로 동시에 실행될 수 있고, 멀티스레드를 쓰는 가장 큰 이유가 이것이다. 코어는 달라도 같은 힙을 보기 때문에 같은 변수를 동시에 고치면 값이 꼬인다. 그래서 락(mutex)이 필요하고, 락이 많을수록 서로 기다리느라 병렬 효과가 줄어든다.

  • Python: GIL 때문에 Python 코드는 한 번에 한 스레드만 실행된다. CPU 작업을 병렬로 돌리려면 multiprocessing(프로세스 여러 개)을 쓴다
  • Node.js: JavaScript 코드는 이벤트 루프 스레드 하나에서 돈다. 여러 코어는 worker_threads나 cluster로 쓴다
  • PHP: 스레드 대신 PHP-FPM이 프로세스를 여러 개 띄워 여러 코어를 쓴다

스레드가 코어에 고정되어 있지는 않아서 실행될 때마다 다른 코어로 옮겨질 수 있다(고정하려면 CPU 어피니티).

ps -L -o pid,lwp,psr,pcpu,comm -p <PID>   # PSR = 마지막에 실행된 논리 코어 번호

Q5.STT 라이선스 채널은 프로세스인가? 채널 수만큼 코어를 잡는 이유는?

채널은 원래 라이선스(사업) 개념으로, 동시에 인식할 수 있는 음성 스트림(통화) 수를 뜻한다. 그 채널을 프로세스로 만들지 스레드로 만들지는 엔진 구현에 달려 있다.

  • 채널 = 프로세스: 채널끼리 메모리가 격리되어 하나가 죽어도 나머지는 산다. 대신 모델을 프로세스마다 올리면 메모리를 많이 쓴다
  • 채널 = 스레드: 모델을 한 번만 올리고 공유해서 메모리 효율이 좋다. 대신 프로세스가 죽으면 모든 채널이 같이 죽는다

STT 디코딩은 CPU 집중 작업이고, 실시간이라면 1초 분량을 1초 안에 처리해야 한다. 이때 쓰는 지표가 RTF(Real-Time Factor) = 처리 시간 ÷ 음성 길이다. RTF 0.3이면 계산상 코어 하나에 3채널도 가능하지만, 통화가 몰리는 순간 처리가 밀리므로 "1채널 = 1코어"로 여유를 두고 설계하는 경우가 많다.

그림 2. 채널 1개가 워커 1개, 워커 1개가 논리 코어 1개를 차지한다. 막대의 RTF 값은 설명용 예시이고 실제 값은 엔진 · CPU마다 측정해야 한다

Q6.회사 엔진은 채널을 vcore(논리 코어) 기준으로 잡는다. 무엇을 조심해야 하나?

vcore 기준이면 채널 2개가 물리 코어 1개를 나눠 쓴다. 8코어 16스레드 서버라면 16채널이 만들어지지만 연산 장치는 8개뿐이다. 엔진의 RTF에 여유가 있으면 문제없고, 빠듯하면 피크 시간에 지연이 생긴다.

  • 성능 검증은 채널 1~2개가 아니라 라이선스 최대 채널을 동시에 걸고 한다. 몇 채널만 돌리면 각 채널이 물리 코어를 혼자 써서 좋게 나온다
  • 웹관리자(Apache · PHP), MariaDB, 녹취 연동이 같은 서버에 있으면 vcore 몇 개는 채널에 쓰지 않고 남긴다
  • 보안 정책으로 SMT를 끈 서버는 vcore가 절반이라 만들 수 있는 채널도 절반이 된다(대신 채널당 성능은 좋다)
  • VM은 vCPU가 이미 하이퍼스레드 하나인 경우가 많고, 호스트 오버커밋이 있으면 더 느리다. 인프라 담당자에게 CPU 예약 여부를 물어본다

사이징할 때는 "vcore 수 = 판매 채널 수"가 아니라 "vcore 수 − 다른 서비스용 여유분"으로 안내하고, 설치할 때 lscpu 결과(물리 코어 수 · 코어당 스레드 수 · VM 여부)를 기록해 둔다.

Q7.CPU 스케줄링도 실무에서 중요한가?

알고리즘을 직접 바꿀 일은 거의 없지만, 원리를 알아야 "STT가 느려요" 같은 문의의 원인을 좁힐 수 있다. Rocky Linux 9(커널 5.14)는 CFS, 커널 6.6 이후는 EEVDF를 쓴다.

  • 런 큐(준비 큐) 길이가 논리 코어 수보다 계속 길면 스레드가 차례를 기다리느라 지연된다 → STT에서는 인식 지연
  • load average는 논리 코어 수와 비교해서 읽는다(리눅스는 디스크 I/O 대기도 포함)
  • 같은 서버에서 야간 배치 · 백업이 STT와 경쟁하면 배치의 nice 값을 올린다
  • 서비스 단위로 CPU를 제한하려면 systemd의 CPUQuota(cgroup)를 쓴다
  • VM에서만 느리면 top의 %st(steal)를 본다
vmstat 1                    # r = 런 큐 길이, cs = 초당 문맥 교환, st = steal
uptime                      # load average 1 · 5 · 15분
top                         # 1 키 = 논리 코어별 사용률
pidstat -w -p <PID> 1       # 프로세스별 문맥 교환 (sysstat)
renice 10 -p <배치 PID>      # 배치 작업 우선순위 낮추기

Q8.32 · 33강 요약: 큐, 선점, 알고리즘을 한 장으로 보면?

준비 큐는 CPU를 기다리는 줄, 대기 큐는 I/O 같은 이벤트를 기다리는 줄이다(요약의 "CPU를 달라고 줄 서는 공간"은 준비 큐에만 맞는다). CPU에서 준비 큐로 돌아가는 화살표(강제 회수)가 있으면 선점형, 없으면 비선점형이다. 알고리즘은 결국 준비 큐에서 다음에 누구를 꺼낼지 정하는 규칙이다.

  • FCFS: 도착 순서대로 · 비선점 · 호위 효과
  • SJF: 다음 CPU 버스트가 짧은 것부터 · 평균 대기 최소 · 기아 (선점형은 SRTF)
  • 라운드 로빈: 타임 슬라이스씩 돌아가며 · 선점 · 슬라이스가 크면 FCFS, 작으면 문맥 교환 비용
  • 우선순위: 높은 것부터 · 기아 → 에이징
  • 다단계 큐: 성격별 큐 · 큐마다 다른 알고리즘 · 큐 사이 이동 없음 → 다단계 피드백 큐는 큐 사이 이동 허용

그림 3. 준비 큐 · 대기 큐 사이의 이동과 선점이 일어나는 자리. 알고리즘별 간트 차트 비교는 CPU 스케줄링 한 장 그림에 있다

Q9.CPU 스케줄링은 프로세스는 많은데 CPU를 효율적으로 쓰려고 줄을 세우는 전략인가?

핵심은 맞다. 세 가지를 덧붙이면 더 정확하다.

  • 목표가 효율 하나가 아니다: 처리량 · 응답 시간 · 공정성 · CPU 사용률이 서로 부딪친다. SJF는 처리량에 좋지만 긴 작업이 굶고, 타임 슬라이스를 줄이면 응답은 좋아져도 문맥 교환 때문에 처리량이 떨어진다. 그래서 서버 · 데스크톱 · 실시간 시스템의 스케줄러가 서로 다른 쪽에 무게를 둔다
  • 줄 세우기만이 아니라 빼앗기(선점)도 절반이다. 선점이 없으면 앞사람이 CPU를 놓지 않는 순간 끝이다
  • 실제로 줄을 서는 단위는 스레드이고, 코어가 여러 개면 줄도 코어마다 있다(코어별 런 큐). 한쪽만 길어지면 다른 코어로 옮겨 균형을 맞춘다

한 문장으로: 한정된 CPU를 여러 실행 단위가 나눠 쓰도록 실행 순서 · 실행 시간 · 실행 위치를 정하는 전략이고, 효율 · 응답성 · 공정성 사이에서 균형을 잡는다.

핵심 정리

  • 코어는 하드웨어, 프로세스 · 스레드는 소프트웨어이고, 스케줄러가 스레드를 논리 코어에 올린다
  • 논리 코어 둘은 물리 코어 하나의 연산 장치를 나눠 쓰므로 성능은 2배가 아니다. 계산이 무거운 작업은 물리 코어 수가 기준
  • 코어당 스레드 수는 CPU마다 다르다(ARM 1 · x86 2 · POWER 4~8), VM은 vCPU 기준
  • 프로세스는 자원의 그릇, 스레드는 CPU 시간을 직접 배정받는 실행 단위다
  • STT 채널은 동시 처리 수(라이선스 개념)이고, 엔진이 채널마다 워커를 만들어 논리 코어 하나씩 차지한다. vcore 기준이면 피크 때 RTF 여유를 확인해야 한다
  • 스케줄링은 효율 · 응답성 · 공정성의 균형이고, 런 큐 · load average · nice · 어피니티 · steal을 읽을 줄 알면 성능 문의를 좁힐 수 있다
