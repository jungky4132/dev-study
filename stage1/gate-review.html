Q1.프로세스와 스레드의 차이는? 메모리를 어떻게 나눠 쓰나?

프로세스는 OS로부터 자원을 할당받은 작업실, 스레드는 그 안에서 일하는 작업자다. 프로세스에는 스레드가 최소 1개 있다.

  • 스레드끼리 공유: 코드 · 데이터(전역 변수) · 힙 · 열린 파일
  • 스레드마다 따로: 스택 · 레지스터(PC 포함)
  • 프로세스끼리는 OS가 주소 공간을 분리(MMU · 페이지 테이블)하므로 통신하려면 IPC(파이프 · 공유 메모리 · 소켓)가 필요하다
  • 스레드는 메모리를 공유하기 때문에 동시에 같은 값을 건드리면 꼬인다(경쟁 조건) → 동기화가 반드시 필요하다
꼬리 1. 스레드 하나가 잘못된 메모리에 접근하면? → CPU가 예외로 감지하고 커널이 그 스레드에 SIGSEGV를 보낸다. 시그널 처리 방식은 프로세스 단위로 공유되고 SIGSEGV의 기본 동작이 "프로세스 종료"라서, 결과적으로 프로세스 전체(모든 스레드)가 종료된다. 단, 스레드가 죽는다고 늘 이렇지는 않다: 스레드 함수가 return하거나 Java · Python에서 처리 안 된 예외로 끝나면 그 스레드만 끝나고 프로세스는 산다(스레드 하나가 죽으면). (죽지 않고 틀린 값으로 계속 도는 "데이터 오염"은 별개 문제)
꼬리 2. 크롬은 왜 탭마다 프로세스를 쓰나? → 스레드끼리의 메모리 접근은 합법이라 CPU가 막지 못한다. 프로세스로 나누면 한 탭의 장애와 악성 코드를 그 탭 안에 가둘 수 있다. 대가는 메모리 · 생성 · 전환 비용과 IPC.

Q2.권한 755는 누구에게 무엇을 허용하나? 디렉터리에 x 권한이 없으면?

7 = 소유자 rwx, 5 = 소유 그룹 r-x, 5 = 기타 사용자 r-x. 같은 r · w · x라도 파일과 디렉터리에서 뜻이 다르다.

  • 파일: r 내용 읽기 · w 내용 수정 · x 실행
  • 디렉터리: r 목록 보기 · w 안에서 파일 만들기 · 지우기 · 이름 바꾸기 · x 진입(이름으로 찾아 들어가기)
  • x 없이 r만: 목록(이름)만 보이고 cd · cat 디렉터리/파일 불가
  • r 없이 x만: 목록은 안 보이지만 이름을 알면 cd · cat 가능
자주 틀리는 점: 파일을 지울 수 있는지는 파일 권한이 아니라 그 파일이 든 디렉터리의 w(+x)로 정해진다. 그래서 755 디렉터리 안의 666 파일은 남이 내용은 고칠 수 있어도 지우지는 못한다.
chmod 644 ~/permtest   # x 없음: ls 됨 / cd · cat 안 됨
chmod 100 ~/permtest   # x만:   ls 안 됨 / cd · cat 됨 (이름을 알 때)

실습 메모: 처음엔 711로 실험했는데 소유자 자리가 7(rwx)이라 소유자로는 차이가 안 보였다. 소유자 자리를 1로 바꿔야 한다.

꼬리 1. Apache로 /home/user/public_html/index.html(644)을 서비스하는데 403이 난다면? → ① error_log 확인 ② namei -l로 경로 전체에 others의 x가 있는지(흔한 원인: /home/user가 700) ③ SELinux(httpd_enable_homedirs, 보안 컨텍스트) ④ UserDir · Require 설정
꼬리 2. 파일이 711이면 다른 사용자가 실행할 수 있나? → 컴파일된 바이너리는 커널이 올려 실행하므로 x만으로 된다. 스크립트는 인터프리터가 파일을 읽어야 하므로 r도 필요하다.

Q3.시스템 콜이 왜 필요한가? 사용자 모드와 커널 모드의 차이는?

사용자 모드와 커널 모드는 CPU의 권한 수준(실행할 수 있는 명령의 범위)이다. "사용자와 상호작용하는 모드"가 아니다 — 화면 없는 데몬도 사용자 모드로 돈다.

  • CPU: 커널 모드에서만 특권 명령(입출력 제어 · 페이지 테이블 교체 · 인터럽트 끄기 등)을 허용하고, 명령마다 검사한다
  • OS: 커널 모드로는 커널 코드만 실행되도록 배치한다(부팅 때 진입 주소를 등록하고, 나머지는 사용자 모드로 내려서 실행)
  • 그래서 사용자 프로그램은 하드웨어 · 자원이 필요하면 시스템 콜로 커널에 서비스를 요청할 수밖에 없다. 커널은 요청을 검사(권한 등)한 뒤 처리하거나 거절한다 — Permission denied가 바로 거절이다
printf("%d개\n", 3)
 → glibc: 포맷 변환 + 버퍼링       (사용자 모드)
 → write(1, "3개\n", 5) → syscall  (커널 모드로 전환)
 → 커널 → 터미널 드라이버 → 화면
꼬리 1. 시스템 콜과 인터럽트는 누가 발생시키나? → 시스템 콜은 프로그램이 스스로 필요한 시점에(동기), 하드웨어 인터럽트는 장치가 아무 때나(비동기). 둘 다 CPU를 커널 모드로 전환한다. 위반 명령 같은 CPU 내부의 예외까지 셋이 커널로 들어가는 길이다.
꼬리 2. 사용자 프로그램이 직접 커널 모드로 바꿀 수 없는 이유 두 가지? → ① 모드를 바꾸는 명령 자체가 특권 명령이다(커널 모드가 되려면 이미 커널 모드여야 하는 모순) ② 정식 경로로 들어가도 CPU는 OS가 등록한 주소로만 점프하므로 실행되는 건 항상 커널 코드다.
꼬리 3. 위반하면 누가 무엇을 하나? → CPU가 예외로 감지해 커널의 처리 루틴으로 넘기고, OS가 판단해 시그널(SIGILL · SIGSEGV)로 종료시킨다. 페이지 폴트처럼 정상 상황이면 해결하고 계속 실행시키기도 한다.

Q4.캐시가 빠른 이유와 메모리 계층 순서

계층(빠른 순): 레지스터 > L1 > L2 > L3(SRAM) > RAM(DRAM) > SSD > HDD. 위로 갈수록 빠르고 작고 비싸다. 단계마다 속도가 자릿수로 달라진다(L1 약 1ns · RAM 약 100ns · SSD 약 100µs · HDD 약 10ms).

  • 빠른 이유(하드웨어): CPU와 물리적으로 가깝고, 리프레시가 필요 없는 SRAM을 쓴다
  • 작아도 효과가 좋은 이유(지역성): 최근 쓴 데이터를 곧 다시 쓰고(시간 지역성), 근처 데이터를 곧 쓴다(공간 지역성). 그래서 캐시 라인(보통 64B) 단위로 한꺼번에 가져온다
꼬리 1. 왜 RAM만큼 크게 안 만드나? → 비싸고 전력 · 발열이 크며, 무엇보다 크게 만들면 느려진다. 그래서 작고 빠른 L1부터 크고 느린 L3까지 나눈다.
꼬리 2. int a[1000][1000]은 행 순서와 열 순서 중 어느 쪽이 빠른가? → C 배열은 행 단위로 연속 저장된다. 행 순서는 64B(int 16개)를 한 번 가져오면 15번 히트하고, 열 순서는 4000B씩 건너뛰어 거의 매번 미스 → RAM까지 간다.

Q5.UTF-8과 EUC-KR이 섞이면 왜 한글이 깨지나?

문자 집합은 글자에 번호를 붙이는 규칙, 인코딩은 그 번호를 바이트로 바꾸는 규칙이다. 한글은 EUC-KR에서 2바이트, UTF-8에서 3바이트다. 저장한 규칙과 다른 규칙으로 읽으면 바이트를 끊는 위치와 해석이 어긋난다.

'가'  UTF-8 : EA B0 80    EUC-KR : B0 A1
UTF-8 → EUC-KR로 읽음 : EA B0 를 한 글자로 → '媛' 같은 한자가 섞임
EUC-KR → UTF-8로 읽음 : B0 는 첫 바이트가 될 수 없음 → '�'
  • 영문은 안 깨진다: 두 인코딩이 ASCII 영역을 같은 1바이트 값으로 저장하기 때문
꼬리. DB는 utf8mb4인데 화면 한글이 깨진다면? → ① SELECT HEX(col)로 저장된 바이트부터 확인('가'가 EAB080이면 저장은 정상) ② PHP 연결 문자셋(mysqli_set_charset($conn,'utf8mb4')) ③ HTTP 헤더 Content-Type과 <meta charset> — 둘이 다르면 헤더가 우선

Q6.서비스가 부팅 때 자동으로 안 뜨면 무엇을 확인하나?

  1. systemctl is-enabled 서비스명 — 부팅 등록 여부. 없으면 systemctl enable --now
  2. systemctl status 서비스명 — 현재 상태와 마지막 에러
  3. journalctl -u 서비스명 -b — 이번 부팅에서 실패한 실제 원인
  4. 의존성(순서) — 네트워크 · DB · 마운트보다 먼저 떠서 실패하지 않았나 (Wants=network-online.target과 After=network-online.target을 함께 쓴다 — Wants만 쓰면 순서는 보장되지 않는다)
  5. SELinux 차단(ausearch -m avc -ts boot) · 설정 파일 오류 · 포트 충돌
systemctl disable chronyd
Removed "/etc/systemd/system/multi-user.target.wants/chronyd.service".
systemctl is-enabled chronyd   # disabled  ← 다음 부팅
systemctl is-active chronyd    # active    ← 지금 (disable은 실행 중인 것을 안 건드림)
systemctl enable chronyd
Created symlink .../multi-user.target.wants/chronyd.service → /usr/lib/systemd/system/chronyd.service.

enable의 실체 = WantedBy=에 적힌 target의 .wants/ 디렉터리에 심볼릭 링크 만들기. 원본 유닛은 /usr/lib/systemd/system/(패키지), 관리자 설정은 /etc/systemd/system/(우선 적용).

꼬리 1. start와 enable의 차이는? → start는 지금 실행, enable은 다음 부팅을 위한 링크. enable --now는 둘을 한 번에. 설치 후 start만 하면 재부팅 때 안 뜬다.
꼬리 2. enable돼 있는데 재부팅하면 안 뜬다면? → 시작은 시도했지만 실패한 것. 의존성 순서, SELinux, 설정 오류를 journalctl로 확인한다. 방화벽은 "떴는데 접속이 안 되는" 다른 증상이다.

핵심 정리

  • 세 문항(프로세스 격리 · 권한 검사 · 시스템 콜)은 한 원리로 이어진다: CPU가 규칙을 강제하고, 커널이 모든 자원 접근을 한곳에서 검사한다
  • 디렉터리의 x는 실행이 아니라 진입, 파일 삭제는 디렉터리의 w
  • 캐시는 하드웨어 덕분에 빠르고, 지역성 덕분에 작아도 효과가 있다
  • 깨진 모양(한자 vs �)으로 어느 방향으로 잘못 읽었는지 알 수 있다
  • enabled = 다음 부팅, active = 지금
