운영체제 · 커널 · 인터럽트 질문 정리

운영체제 전체가 커널 영역에 들어가는지, root와 커널 모드는 같은지, 시스템 콜은 왜 인터럽트인지 등 강의를 들으며 생긴 질문 8개를 그림 3장으로 정리 · STAGE 1 운영체제 · 2026-11-09

Q1.운영체제의 일부가 아니라 전체가 커널 영역에 들어가나?

아니다. 커널 영역에는 운영체제의 핵심인 커널만 있다. 교재가 운영체제와 커널을 거의 같은 뜻으로 써서 “운영체제는 커널 영역에 적재된다”고 단순화한 것이다.

  • 커널 영역: 프로세스 관리, 메모리 관리, 파일 시스템, 장치 드라이버, 시스템 콜 처리
  • 사용자 영역: 셸(bash), systemd, sshd, dnf 같은 나머지 운영체제 구성 요소. OS와 함께 설치되지만 일반 프로세스처럼 사용자 모드에서 실행된다

커널에 무엇을 넣을지는 설계마다 다르다. 리눅스는 대부분을 커널 안에 두는 모놀리식 커널, QNX 같은 마이크로커널은 최소 기능만 커널에 두고 나머지는 사용자 영역으로 뺀다.

그림 1. 커널 영역에는 커널만 있고, 운영체제의 나머지 구성 요소와 응용 프로그램은 사용자 영역에서 시스템 콜로 요청한다

Q2.강의에서 운영체제를 국가 자원을 관리하는 정부에 비유하던데?

한정된 자원을 여러 국민에게 공정하게 나눠 주는 정부처럼, 운영체제는 CPU · 메모리 · 저장장치 · 입출력장치를 여러 프로그램에 나눠 준다.

  • 국민 → 프로세스, 국가 자원 → 하드웨어 자원
  • 배분 → 스케줄링 · 메모리 할당, 법과 규제 → 보호와 권한
  • 민원 창구 → 시스템 콜, 창구 뒤 공무원 → 커널

다만 운영체제는 타이머 인터럽트로 CPU를 강제로 회수(선점)하고 규칙을 어긴 프로그램을 바로 종료할 만큼 통제권이 강하다. 그래도 목적은 체제 유지가 아니라 프로그램이 잘 돌아가게 하는 것이라, 공정성(에이징)과 서비스(시스템 콜 처리)를 기본으로 한다. “권한은 강하지만 그 권한을 봉사에 쓰는 정부”가 가장 가깝다.

Q3.운영체제에 요청하는 게 Windows API를 부르는 건가?

거의 맞다. 다만 Windows API는 요청을 위한 창구 역할의 라이브러리이고, 실제로 커널에 들어가는 동작은 그 안쪽의 시스템 콜이다.

CreateFile()                ← Windows API (사용자 모드)
 → kernel32.dll / KernelBase.dll
 → ntdll.dll: NtCreateFile() ← 아직 사용자 모드
 → syscall 명령어            ← 커널 모드로 전환
 → ntoskrnl.exe가 파일 처리   ← 커널 모드
  • Windows는 시스템 콜 번호를 공개하지 않고 버전마다 바꾸므로 API가 공식 창구다
  • 모든 API가 커널까지 가지는 않는다. 문자열 처리처럼 사용자 모드에서 끝나는 함수도 있다
  • 리눅스도 같다: fopen() → glibc의 open() → openat 시스템 콜. PHP의 file_get_contents()도 결국 openat · read로 내려간다 (strace php test.php로 확인)

Q4.그러면 운영체제는 민원실 역할을 하는 건가?

프로그램 입장에서는 그렇다. 정확히 나누면 민원 창구 = 시스템 콜, 창구 뒤에서 처리하는 공무원 = 커널, 정부 전체 = 운영체제다.

운영체제는 요청을 기다리기만 하지 않는다. 민원이 없어도 타이머 인터럽트로 CPU를 다음 프로세스에 넘기고, 메모리를 정리하고, 키보드 · 네트워크 같은 장치의 인터럽트를 처리한다. “프로그램이 보기엔 민원실, 실제로는 나라 전체를 운영하는 정부”.

Q5.사용자 모드는 일반 계정, 커널 모드는 root 계정인가?

아니다. 둘은 다른 개념이다.

  • 사용자 모드 / 커널 모드: CPU의 실행 권한 수준. 하드웨어가 구분한다 (x86의 Ring 3 / Ring 0)
  • 일반 계정 / root: 커널이 관리하는 사용자 권한 정보. 커널이 요청을 허락할지 판단할 때 쓴다
일반 계정: open("/etc/shadow") → 커널: 거부 (Permission denied)
root 계정: open("/etc/shadow") → 커널: 허가 → 커널 모드에서 읽기

root로 실행한 프로그램도 사용자 모드에서 돌아가고 똑같이 시스템 콜로 요청한다. root는 거절당하지 않는 VIP 민원인일 뿐, 창구를 건너뛰고 청사 안에 들어가 직접 일하지는 못한다.

Q6.커널 모드를 쓰려면 시스템 호출을 거쳐야 하고, 그러면 시스템이 커널 영역에 들어가 처리해 주나?

맞다. 두 가지만 정확히 하면 된다. 프로그램 코드가 커널 모드로 실행되는 일은 없고(커널 코드가 실행된다), 모드를 바꾸는 주체는 CPU다.

  • ① 프로그램이 read() 호출 → 결국 syscall 명령어 실행
  • ② CPU가 하던 일을 저장하고 커널 모드로 전환, 커널이 정해 둔 진입 지점으로 점프
  • ③ 커널이 시스템 콜 번호를 보고 처리 (권한 확인, 디스크 읽기)
  • ④ 결과를 돌려주며 사용자 모드로 복귀, 프로그램은 멈춘 다음 줄부터 실행

정리: 사용자 프로그램은 시스템 콜로 요청만 하고, CPU가 커널 모드로 바뀌면 커널이 대신 처리한 뒤 결과를 돌려준다.

Q7.시스템 콜을 요청하는 게 인터럽트로 보이는데?

맞다. 시스템 콜은 프로그램이 일부러 일으키는 소프트웨어 인터럽트(트랩)다. 32비트 리눅스에서는 코드에 그대로 드러났다.

mov eax, 4      ; 시스템 콜 번호 (write)
int 0x80        ; 0x80번 인터럽트 발생 → 커널로 진입

64비트 CPU는 인터럽트 벡터를 거치지 않는 전용 명령어 syscall을 써서 더 빠르지만, 저장 → 커널 처리 → 복귀 구조는 같다.

  • 동기 인터럽트 (명령어 실행 때문에 발생): 소프트웨어 인터럽트(시스템 콜, 의도적) · 예외(0 나누기, 페이지 폴트)
  • 비동기 인터럽트 (외부에서 발생): 하드웨어 인터럽트(타이머, 키보드, 네트워크)

그림 2. 세 종류 인터럽트 모두 같은 흐름(상태 저장 → 커널 모드 전환 → 벡터로 처리 루틴 실행 → 복귀)을 탄다. 원인만 다르다

Q8.운영체제가 해 주는 서비스는?

  • 프로세스 관리 · CPU 스케줄링: 여러 프로그램이 CPU를 나눠 쓰게 한다
  • 메모리 관리: 프로그램마다 메모리를 할당하고 회수한다
  • 파일 · 입출력 관리: 디스크의 파일과 각종 장치를 다룬다
  • 보호 · 보안: 모든 서비스에 공통. 요청마다 권한을 확인하고 다른 프로세스의 영역 침범을 막는다 (root와 일반 계정의 차이가 여기서 판단된다)

어느 서비스든 신청 창구는 시스템 콜 하나다.

그림 3. 운영체제 서비스와 담당 하드웨어

핵심 정리

  • 커널 영역에는 운영체제의 핵심인 커널만 있고, 셸 · systemd 같은 나머지는 사용자 모드에서 실행된다
  • 프로그램은 API(라이브러리)를 부르고, 그 안에서 시스템 콜로 커널에 요청한다
  • 사용자 · 커널 모드는 CPU의 권한 수준, root · 일반 계정은 커널이 관리하는 권한 정보로 서로 다르다
  • 시스템 콜 · 예외 · 하드웨어 인터럽트는 모두 같은 인터럽트 흐름으로 커널에 들어가고, 원인만 다르다
  • 운영체제 서비스: 프로세스 · CPU 스케줄링 · 메모리 · 파일과 입출력, 그리고 모두에 공통인 보호 · 보안
