데이터 표현

2진수

1945

Binary

시대적 배경
1940년대 초 ENIAC 같은 최초의 전자식 컴퓨터는 10진수로 계산했고, 프로그램을 바꾸려면 전선을 다시 꽂아야 했다. 1945년 폰 노이만의 EDVAC 보고서가 프로그램도 데이터처럼 메모리에 저장하고, 수는 2진수로 다루자고 제안했다.
그래서 생긴 문제
진공관 같은 전자 부품은 전압이 있다/없다 두 상태는 안정적으로 구분하지만, 10단계를 정확히 구분하기는 어렵고 회로도 복잡해진다.
개념
0과 1 두 숫자만으로 수를 나타내는 방법. 컴퓨터의 명령어 · 숫자 · 문자 · 그림은 모두 결국 2진수로 저장되고 처리된다.
지금은
모든 디지털 컴퓨터의 기본이다.

관련 그림: 데이터 · 인코딩

16진수

1964

Hexadecimal

시대적 배경
1964년 IBM System/360이 8비트를 1바이트로 정하면서 바이트 단위 컴퓨터가 표준이 됐다. 8비트는 4비트씩 딱 둘로 나뉜다.
그래서 생긴 문제
2진수는 사람이 읽고 쓰기에 너무 길어서, 메모리 주소나 바이트 값을 다룰 때 실수가 잦았다.
개념
0~9와 A~F 16개 기호로 수를 나타내는 방법. 2진수 4자리가 16진수 1자리와 정확히 대응해서, 1바이트는 16진수 2자리로 쓴다.
지금은
메모리 주소, 색상 코드(#FF0000), 인코딩 바이트(ED 95 9C) 표기에 쓴다.

관련 그림: 데이터 · 인코딩

2의 보수

1945 · 1964

Two's complement

시대적 배경
초기 컴퓨터들은 음수를 부호 비트로만 표시하는 등 제각각의 방식을 썼다. 폰 노이만이 1945년 EDVAC 보고서에서 2의 보수를 제안했고, 1964년 IBM System/360이 채택하면서 사실상 표준이 됐다.
그래서 생긴 문제
부호 비트만 쓰는 방식은 +0과 −0이 따로 생기고, 덧셈과 뺄셈에 서로 다른 회로가 필요해 하드웨어가 비싸졌다.
개념
양수의 모든 비트를 뒤집고 1을 더해 음수를 나타내는 방식. 0이 하나뿐이고, 뺄셈을 덧셈 회로로 처리할 수 있다.
지금은
오늘날 거의 모든 CPU가 정수를 2의 보수로 다룬다.

관련 그림: 데이터 · 인코딩

ASCII

1963

American Standard Code for Information Interchange

시대적 배경
1950~60년대에는 제조사마다 문자 코드가 달라서, 같은 글자도 기계마다 다른 번호로 저장했다. 컴퓨터와 텔레타이프 같은 통신 장비를 연결하는 일이 늘어나던 시기였다.
그래서 생긴 문제
서로 다른 회사의 기계끼리 데이터를 주고받으면 글자가 엉뚱하게 바뀌었다.
개념
영문자 · 숫자 · 기호 · 제어 문자 128개에 0~127 번호를 붙인 7비트 문자 표준. 1963년 미국 표준협회가 제정했다.
지금은
UTF-8과 EUC-KR 모두 영문 부분은 ASCII와 같아서, 지금도 모든 인코딩의 바탕이다.

관련 그림: 데이터 · 인코딩

문자 집합과 인코딩

1960~80년대

Character set · Encoding

시대적 배경
ASCII가 퍼진 뒤 컴퓨터가 영어권 밖으로 확산됐다. 나라마다 자기 문자를 담기 위해 한국은 KS C 5601(1987), 일본은 JIS처럼 문자 표와 저장 방식을 따로 만들었다.
그래서 생긴 문제
ASCII 128자로는 한글 · 한자를 담을 수 없었다. 그런데 나라별 방식이 생기자, 다른 방식으로 저장된 문서를 열면 글자가 깨지는 새 문제가 생겼다.
개념
문자 집합은 문자마다 번호를 정한 표, 인코딩은 그 번호를 실제 저장할 바이트로 바꾸는 규칙이다. 저장할 때와 읽을 때 같은 인코딩을 써야 글자가 복원된다.
지금은
대부분 UTF-8로 통일됐지만, 오래된 시스템 · DB에는 EUC-KR이 남아 있어 한글 깨짐의 흔한 원인이 된다.

관련 그림: 데이터 · 인코딩

EUC-KR

1987~

Extended Unix Code - Korean

시대적 배경
1987년 한글 완성형 문자 집합 KS C 5601(지금의 KS X 1001)이 국가 표준이 됐다. 자주 쓰는 한글 2,350자와 한자 · 기호를 담았고, 이를 저장하는 방식으로 EUC-KR이 PC 통신과 초기 인터넷에서 널리 쓰였다.
그래서 생긴 문제
ASCII와 섞어 쓸 수 있으면서 한글을 표현할 방법이 필요했다.
개념
KS X 1001의 글자를 2바이트로 저장하는 인코딩. 영문은 ASCII와 같은 1바이트다. 표에 없는 일부 한글은 표현할 수 없다는 한계가 있었다.
지금은
윈도우의 CP949(확장 완성형)와 함께 오래된 한국어 시스템에 남아 있다.

관련 그림: 데이터 · 인코딩

유니코드

1991

Unicode

시대적 배경
1980년대 말에는 나라별 문자 집합이 수십 가지였다. 한 문서에 한국어와 일본어를 함께 쓰거나, 해외 시스템과 데이터를 주고받으면 충돌이 잦았다. 1991년 유니코드 1.0이 발표됐다.
그래서 생긴 문제
나라별 문자 집합끼리는 같은 번호가 서로 다른 글자를 뜻해서 섞어 쓸 수 없었다.
개념
전 세계 문자에 겹치지 않는 하나의 번호(코드 포인트)를 붙인 통합 문자 집합. 예: 한 = U+D55C.
지금은
현대 한글 11,172자는 1996년 유니코드 2.0부터 모두 들어 있다. 이모지도 유니코드 문자다.

관련 그림: 데이터 · 인코딩

UTF-8

1992

Unicode Transformation Format - 8bit

시대적 배경
유니코드가 나왔지만 모든 글자를 2~4바이트로 저장하면 기존 ASCII 파일과 프로그램이 깨졌다. 1992년 켄 톰프슨과 롭 파이크가 벨 연구소의 Plan 9 운영체제를 위해 UTF-8을 설계했다.
그래서 생긴 문제
이미 세상에 있는 수많은 ASCII 문서 · 프로그램과 호환되면서 유니코드를 쓸 방법이 필요했다.
개념
유니코드 번호를 1~4바이트로 저장하는 인코딩. 영문은 ASCII와 똑같은 1바이트, 한글은 3바이트다.
지금은
웹 페이지 대부분과 리눅스(ko_KR.UTF-8 등)의 기본 인코딩이다.

관련 그림: 데이터 · 인코딩

CPU

레지스터

1945

Register

시대적 배경
1945년 폰 노이만 구조가 정해지면서, CPU가 메모리에서 명령어와 데이터를 가져와 처리하는 방식이 표준이 됐다.
그래서 생긴 문제
메모리는 CPU보다 훨씬 느려서, 계산 도중의 값을 매번 메모리에 두면 CPU가 계속 기다려야 했다.
개념
CPU 안에 있는 아주 작고 빠른 저장 공간. 지금 처리 중인 명령어 · 데이터 · 주소를 잠시 담는다.
지금은
메모리 계층의 맨 위에 있다.

관련 그림: CPU 레지스터 · 메모리 계층

프로그램 카운터 (PC)

1945

Program Counter

시대적 배경
폰 노이만 구조에서 프로그램은 메모리에 차례로 저장되고, CPU가 하나씩 꺼내 실행하게 됐다.
그래서 생긴 문제
CPU는 지금 어디까지 실행했는지 기억해야 다음 명령어를 가져올 수 있고, 조건에 따라 다른 곳으로 건너뛸 수도 있어야 했다.
개념
다음에 실행할 명령어의 주소를 담는 레지스터. 명령어를 가져올 때마다 다음 주소로 바뀌고, 점프 · 함수 호출 때는 다른 주소로 덮어쓰인다.
지금은
x86에서는 IP(명령어 포인터)라고 부른다.

관련 그림: CPU 레지스터

ALU

1945

Arithmetic Logic Unit

시대적 배경
폰 노이만이 EDVAC 보고서에서 컴퓨터를 연산 장치 · 제어 장치 · 메모리 · 입출력으로 나누어 정의했다.
그래서 생긴 문제
모든 계산은 결국 산술 연산과 논리 연산의 조합이라, 이를 전담하는 회로가 필요했다.
개념
덧셈 · 뺄셈 같은 산술 연산과 AND · OR 같은 논리 연산을 하는 CPU 회로. 결과의 상태를 플래그 레지스터에 남긴다.
지금은
현대 CPU는 코어마다 여러 개의 ALU를 둔다.

관련 그림: CPU 레지스터

제어장치

1945

Control Unit

시대적 배경
폰 노이만 구조의 네 구성 요소 중 하나로 정의됐다.
그래서 생긴 문제
명령어마다 해야 할 일이 달라서, 명령어를 읽고 각 부품이 언제 무엇을 할지 지휘하는 역할이 필요했다.
개념
명령어를 해석하고 ALU · 레지스터 · 메모리 · 입출력에 제어 신호를 보내는 CPU 회로.

관련 그림: CPU 레지스터

명령어 사이클

1945

Instruction cycle

시대적 배경
프로그램 내장 방식이 도입되면서, 사람이 전선을 바꾸는 대신 CPU가 메모리의 명령어를 스스로 실행하게 됐다.
그래서 생긴 문제
저장된 프로그램을 자동으로 실행하려면 정해진 반복 동작이 필요했다.
개념
인출(메모리에서 명령어 가져오기) → 해석 → 실행을 반복하는 CPU의 기본 동작 순서.
지금은
현대 CPU는 이 단계를 겹쳐서 실행(파이프라인)하지만 기본 순서는 같다.

관련 그림: CPU 레지스터

스택 포인터

1960~70년대

Stack Pointer

시대적 배경
1950년대 말 서브루틴(함수)이 널리 쓰이고, 함수 안에서 또 함수를 부르는 프로그램이 많아졌다. 1961년 버로스 B5000 같은 스택 기반 컴퓨터를 거쳐 PDP-11(1970), 인텔 8080(1974) 등 대부분의 CPU가 전용 스택 포인터를 갖게 됐다.
그래서 생긴 문제
함수 호출이 중첩되면 돌아갈 주소와 지역 변수를 순서대로 쌓았다가 거꾸로 꺼내야 했다.
개념
메모리의 스택 영역에서 현재 꼭대기 위치를 가리키는 레지스터. push · pop 때마다 바뀐다.
지금은
재귀 함수, 인터럽트 처리 때의 상태 백업이 모두 스택을 쓴다.

관련 그림: CPU 레지스터 · 프로세스 · 스레드

플래그 레지스터

초기 컴퓨터~

Flags register

시대적 배경
프로그램에 if 같은 조건 분기가 쓰이기 시작하면서, CPU가 직전 계산 결과를 기억할 필요가 생겼다.
그래서 생긴 문제
조건 점프를 하려면 앞 연산의 결과가 0이었는지, 음수였는지 같은 정보가 남아 있어야 했다.
개념
연산 결과의 상태(0 · 음수 · 올림 · 오버플로)와 CPU 상태(인터럽트 허용 등)를 비트로 담는 레지스터.
지금은
인터럽트 비트로 하드웨어 인터럽트를 받을지 말지도 정한다.

관련 그림: CPU 레지스터 · 입출력 방식

인터럽트

1953~1954

Interrupt

시대적 배경
1950년대 초 컴퓨터는 CPU가 카드 리더 · 프린터 같은 느린 장치를 직접 기다렸다. 1953년 UNIVAC 1103A가 인터럽트를 처음 사용한 것으로 알려져 있고, 1954년 DYSEAC가 하드웨어 인터럽트를 썼다.
그래서 생긴 문제
CPU가 느린 장치를 계속 확인(폴링)하며 기다리면, 비싼 컴퓨터 시간의 대부분이 낭비됐다.
개념
장치나 프로그램이 CPU에 지금 처리할 일이 생겼다고 알려, 하던 일을 잠시 멈추고 처리하게 하는 신호.
지금은
키보드 입력, 네트워크 수신, 타이머(스케줄링) 등 운영체제 동작의 기본이다.

관련 그림: CPU 레지스터 · 입출력 방식

인터럽트 서비스 루틴 (ISR)

1950~60년대

Interrupt Service Routine

시대적 배경
인터럽트가 도입되자, 장치마다 인터럽트가 왔을 때 해야 할 일이 서로 달랐다.
그래서 생긴 문제
키보드 입력 처리와 디스크 완료 처리는 내용이 전혀 달라서, 각각 전용 코드가 필요했다.
개념
특정 인터럽트가 발생했을 때 실행되는 처리 프로그램(인터럽트 핸들러). 끝나면 원래 하던 작업으로 돌아간다.
지금은
리눅스에서는 장치 드라이버 안에 들어 있다.

관련 그림: CPU 레지스터 · 입출력 방식

인터럽트 벡터

1960~70년대

Interrupt vector

시대적 배경
연결된 장치가 많아지면서, 인터럽트가 왔을 때 누가 불렀는지 CPU가 장치마다 물어보는 방식이 느려졌다. 인텔 8080 · 8086 계열도 번호로 처리하는 벡터 방식을 썼다.
그래서 생긴 문제
어떤 장치의 인터럽트인지 하나씩 확인하면 처리가 늦어졌다.
개념
인터럽트마다 정해진 번호와, 그 번호에 해당하는 ISR 시작 주소의 목록(벡터 테이블).

관련 그림: CPU 레지스터

MMU

1960년대

Memory Management Unit

시대적 배경
1960년대에 한 컴퓨터에서 여러 프로그램을 동시에 메모리에 올려 번갈아 실행하는 다중 프로그래밍 · 시분할 시스템이 퍼졌다. CDC 6600(1964)은 재배치 레지스터와 길이 레지스터로 주소를 바꾸고 범위를 검사했고, 1962년 맨체스터 대학의 Atlas는 페이징 방식의 가상 메모리를 처음 구현했다.
그래서 생긴 문제
프로그램이 메모리 어디에 올라갈지 미리 알 수 없었고, 한 프로그램의 실수가 다른 프로그램이나 운영체제 영역을 망가뜨릴 수 있었다.
개념
CPU 칩 안에서 논리 주소를 물리 주소로 바꾸고, 허락된 범위 밖의 접근을 막는 하드웨어.
지금은
현대 CPU의 MMU는 페이지 테이블과 TLB로 같은 일을 한다.

관련 그림: MMU · CPU 레지스터

베이스 레지스터

1960년대

Base register

시대적 배경
다중 프로그래밍으로 같은 프로그램이 매번 다른 메모리 위치에 올라가게 됐다. IBM System/360(1964) 등은 기준 주소 + 변위 방식의 주소 지정을 널리 썼다.
그래서 생긴 문제
프로그램 속 주소를 실행할 때마다 고쳐 쓰는 것은 번거롭고 느렸다.
개념
기준 주소를 담는 레지스터. 기준 주소 + 오프셋으로 실제 위치를 계산한다. MMU에서는 프로그램이 올라간 시작 주소다.

관련 그림: MMU · CPU 레지스터

한계 레지스터

1960년대

Limit register

시대적 배경
베이스 레지스터와 함께, 여러 프로그램이 한 메모리를 나눠 쓰는 다중 프로그래밍 시대에 도입됐다.
그래서 생긴 문제
한 프로그램이 범위를 넘어 다른 프로그램이나 운영체제 영역을 덮어쓸 수 있었다.
개념
프로그램이 쓸 수 있는 크기를 담는 레지스터. MMU가 논리 주소가 이 값보다 작은지 먼저 검사한다.

관련 그림: MMU

메모리

메모리 계층

1946

Memory hierarchy

시대적 배경
1946년 버크스 · 골드스타인 · 폰 노이만의 보고서가 이미 크고 빠른 메모리는 만들 수 없으니 여러 단계의 메모리가 필요하다고 지적했다.
그래서 생긴 문제
빠른 메모리는 비싸고 작고, 크고 싼 메모리는 느리다. 셋을 다 갖춘 메모리는 없었다.
개념
레지스터 → 캐시 → RAM → 보조기억장치처럼 빠르고 작은 것부터 느리고 큰 것까지 층으로 나눈 구조. 자주 쓰는 데이터를 위쪽에 둔다.
지금은
CPU와 메모리의 속도 차이가 커질수록 계층이 더 세분화됐다(L1 · L2 · L3).

관련 그림: 메모리 계층

캐시

1965 · 1968

Cache memory

시대적 배경
1960년대 들어 CPU가 빨라지는 속도를 메모리가 따라가지 못했다. 1965년 모리스 윌크스가 slave memory라는 이름으로 아이디어를 냈고, 1968년 IBM System/360 Model 85에 처음 상용으로 들어가면서 캐시라는 이름이 붙었다.
그래서 생긴 문제
CPU가 메모리를 기다리는 시간이 전체 성능을 좌우하게 됐다.
개념
CPU와 RAM 사이에서 자주 쓰는 데이터를 복사해 두는 작고 빠른 메모리. 있으면 히트, 없으면 미스.
지금은
지금은 CPU 칩 안에 L1 · L2 · L3가 들어 있다.

관련 그림: 메모리 계층

참조 지역성

1968

Locality of reference

시대적 배경
1960년대 가상 메모리와 캐시가 등장하면서, 작은 빠른 메모리가 왜 효과가 있는지 설명이 필요했다. 1968년 피터 데닝이 작업 집합(working set) 연구에서 이 성질을 정리했다.
그래서 생긴 문제
어떤 데이터를 빠른 메모리에 남겨야 하는지 판단할 기준이 없었다.
개념
프로그램이 방금 쓴 데이터를 또 쓰고(시간 지역성), 근처 주소를 곧 쓰는(공간 지역성) 경향.
지금은
캐시 · 가상 메모리 · 디스크 캐시 설계의 근거다.

관련 그림: 메모리 계층

RAM (메인 메모리)

1970

Random Access Memory

시대적 배경
1950~60년대 주기억장치는 작은 자석 고리를 엮은 자기 코어 메모리였다. 1970년 인텔 1103 DRAM 칩이 나오면서 반도체 메모리가 코어 메모리를 대체하기 시작했다.
그래서 생긴 문제
코어 메모리는 손으로 엮어 만들어 비싸고 크기를 줄이기 어려웠다.
개념
CPU가 실행할 프로그램과 데이터를 올려 두는 주기억장치. 전원이 꺼지면 내용이 사라진다.
지금은
DDR4 · DDR5 같은 DRAM이 쓰인다.

관련 그림: 메모리 계층 · 프로세스 · 스레드

페이징 · 가상 메모리

1962

Paging · Virtual memory

시대적 배경
1962년 맨체스터 대학의 Atlas 컴퓨터가 처음 구현했다. 당시 메모리는 매우 작고 비싸서, 프로그래머가 디스크와 메모리 사이에서 데이터를 직접 옮겨야 했다.
그래서 생긴 문제
프로그램 크기가 메모리보다 크면 실행할 수 없었고, 베이스 · 한계 방식은 프로그램을 연속된 한 덩어리로 올려야 해서 빈 공간이 조각났다.
개념
메모리를 같은 크기의 페이지로 나누고 페이지 테이블로 주소를 바꾸는 방식. 실제 메모리보다 큰 주소 공간을 쓸 수 있다(가상 메모리).
지금은
리눅스 · 윈도우 등 현대 운영체제의 기본이다. STAGE 5에서 자세히 다룬다.

관련 그림: MMU

TLB

1960년대

Translation Lookaside Buffer

시대적 배경
페이징이 도입되자 주소를 바꿀 때마다 메모리에 있는 페이지 테이블을 읽어야 했다. Atlas와 IBM System/360 Model 67(1960년대) 등이 최근 변환 결과를 저장하는 연관 메모리를 두었다.
그래서 생긴 문제
메모리 접근마다 페이지 테이블 조회가 붙어 속도가 크게 느려졌다.
개념
MMU 안에서 최근의 주소 변환 결과를 기억하는 작은 캐시. 지역성 덕분에 대부분 여기서 바로 찾는다.

관련 그림: MMU

저장장치

HDD

1956

Hard Disk Drive

시대적 배경
1950년대 대용량 저장장치는 자기 테이프였고, 원하는 데이터를 찾으려면 처음부터 감아 가며 읽어야 했다. 1956년 IBM 350 RAMAC이 첫 하드디스크로 나왔다(지름 24인치 원판 50장, 약 3.75MB).
그래서 생긴 문제
원하는 위치로 바로 가서 읽는(임의 접근) 대용량 저장장치가 필요했다.
개념
자기 원판(플래터)을 회전시키고 헤드로 읽고 쓰는 보조기억장치.
지금은
용량당 가격이 싸서 대용량 저장 · 백업에 여전히 쓰인다.

관련 그림: 보조기억장치 · RAID

플래시 메모리

1984 · 1987

Flash memory

시대적 배경
1980년대 도시바의 마스오카 후지오가 전원 없이도 내용이 남고 전기로 한 번에 지울 수 있는 메모리를 발명했다. 1984년 NOR형, 1987년 NAND형이 발표됐다.
그래서 생긴 문제
하드디스크보다 작고, 충격에 강하고, 움직이는 부품이 없는 저장장치가 필요했다.
개념
셀에 가둔 전자의 양으로 값을 저장하는 반도체 메모리. 덮어쓰기가 안 되고 블록 단위로만 지울 수 있다.
지금은
USB 메모리 · 스마트폰 · SSD의 저장 매체다.

관련 그림: SSD 수명 · 보조기억장치

SSD

2000년대

Solid State Drive

시대적 배경
2000년대 후반 낸드 플래시 가격이 빠르게 내려가면서 노트북과 서버에 대중화됐다.
그래서 생긴 문제
HDD는 헤드가 움직이는 시간 때문에 임의 접근이 느려서, CPU와 메모리에 비해 큰 병목이었다.
개념
낸드 플래시와 컨트롤러로 만든 보조기억장치. 회전 부품이 없어 HDD보다 훨씬 빠르다.
지금은
NVMe SSD는 PCIe에 직접 연결돼 더 빠르다.

관련 그림: SSD 수명 · 보조기억장치

SLC · MLC · TLC · QLC

1990년대 말~2018

Single / Multi / Triple / Quad Level Cell

시대적 배경
셀 하나에 1비트(SLC)를 담던 방식에서 출발해, 용량 경쟁 속에 MLC · TLC를 거쳐 2018년 QLC 소비자용 SSD가 나왔다.
그래서 생긴 문제
같은 칩 면적에 더 많은 데이터를 담아 용량당 가격을 낮춰야 했다.
개념
셀 하나에 1 · 2 · 3 · 4비트를 저장하는 낸드 방식. 비트가 많을수록 크고 싸지만, 느리고 수명이 짧다.
지금은
소비자용은 TLC · QLC, 고내구성 용도는 SLC · MLC를 쓴다.

관련 그림: 보조기억장치 · SSD 수명

SLC 캐시

2010년대

SLC cache

시대적 배경
TLC SSD가 대중화되던 2013년, 삼성 840 EVO의 TurboWrite처럼 일부 셀을 SLC처럼 쓰는 기법이 쓰였다.
그래서 생긴 문제
TLC · QLC는 쓰기가 느려서 체감 속도가 떨어졌다.
개념
TLC · QLC 셀 일부를 1비트처럼 써서 쓰기를 빠르게 받아 두고, 한가할 때 본 영역으로 옮기는 방식.
지금은
캐시가 가득 차면 쓰기 속도가 급락하는 쓰기 절벽이 생긴다.

관련 그림: 보조기억장치

FTL

1990년대

Flash Translation Layer

시대적 배경
1990년대 플래시를 디스크처럼 쓰려는 저장장치가 나오면서 도입됐다.
그래서 생긴 문제
운영체제는 같은 주소에 다시 쓰기를 기대하지만, 플래시는 덮어쓰기가 안 되고 블록 단위로만 지워진다.
개념
운영체제가 보는 논리 주소를 실제 플래시 위치로 바꿔 주는 SSD 컨트롤러 속 소프트웨어. 새 위치에 쓰고 주소표만 바꾼다. MMU와 비슷한 역할이다.

관련 그림: SSD 수명 · 보조기억장치

가비지 컬렉션 (SSD)

1990~2000년대

Garbage collection

시대적 배경
플래시가 블록 단위로만 지워진다는 물리적 한계 때문에 플래시 저장장치와 함께 필요해졌다.
그래서 생긴 문제
수정할 때마다 옛 페이지가 무효로 남아서, 정리하지 않으면 빈 페이지가 바닥났다.
개념
무효 페이지가 쌓인 블록에서 유효 페이지만 다른 블록으로 옮기고, 그 블록을 통째로 지우는 SSD 내부 정리 작업.
지금은
프로그래밍 언어의 가비지 컬렉션(메모리 자동 해제)과는 이름만 같고 다른 개념이다.

관련 그림: SSD 수명

쓰기 증폭

2000년대 후반

Write amplification

시대적 배경
SSD가 대중화되면서 가비지 컬렉션이 만드는 추가 쓰기가 수명과 성능을 깎는다는 사실이 주목받았다.
그래서 생긴 문제
사용자가 쓴 양만으로는 SSD 수명을 예측할 수 없었다.
개념
호스트가 쓴 양보다 SSD가 실제로 플래시에 쓴 양이 많아지는 현상. WAF = 실제 쓰기 ÷ 요청한 쓰기.
지금은
TRIM · 오버프로비저닝의 효과를 보는 지표다.

관련 그림: SSD 수명

웨어 레벨링

1990년대

Wear leveling

시대적 배경
플래시 셀은 지우기 · 쓰기 횟수(P/E)에 한계가 있다는 것이 초기 플래시 저장장치부터 알려져 있었다.
그래서 생긴 문제
자주 바뀌는 데이터가 한 블록에 몰리면 그 블록만 먼저 수명이 끝났다.
개념
쓰기를 모든 블록에 고르게 나눠 특정 블록만 닳지 않게 하는 기법.

관련 그림: SSD 수명 · 보조기억장치

TRIM

2009~2010

TRIM

시대적 배경

그래서 생긴 문제
파일을 지워도 운영체제만 알고 SSD는 몰라서, 필요 없는 데이터를 가비지 컬렉션 때 계속 옮기는 낭비가 생겼다.
개념

지금은
리눅스는 fstrim.timer로 주기적으로 실행한다.

관련 그림: SSD 수명 · 보조기억장치

RAID

1987

Redundant Array of Inexpensive(Independent) Disks

시대적 배경
1980년대 대형 컴퓨터용 디스크(SLED)는 매우 비쌌고, PC용 작은 디스크는 싸졌다. 1987년 UC 버클리의 패터슨 · 깁슨 · 카츠가 값싼 디스크 여러 개로 비싼 대형 디스크를 대신하자는 논문을 냈다.
그래서 생긴 문제
작은 디스크를 많이 쓰면 그중 하나가 고장 날 확률이 커졌다.
개념
여러 디스크를 묶어 하나처럼 쓰면서 속도(스트라이핑)나 안정성(미러링 · 패리티)을 얻는 기술.
지금은

DMA

1950년대 말~

Direct Memory Access

시대적 배경

그래서 생긴 문제

개념
CPU를 거치지 않고 장치와 메모리가 직접 데이터를 주고받게 하는 방식. DMA 컨트롤러가 전송을 맡고 끝나면 인터럽트로 알린다.
지금은
현대 장치(NVMe · 네트워크 카드)는 장치 안에 DMA 기능이 들어 있다(버스 마스터링).

개념

먼저 온 순서대로 끝까지 실행하는 스케줄링. 긴 작업 뒤에서 짧은 작업이 오래 기다리는 호위 효과가 생긴다.

SJF

일괄 처리 시대

Shortest Job First

시대적 배경

그래서 생긴 문제
FCFS에서는 짧은 작업도 긴 작업 뒤에서 오래 기다렸다.
개념
실행 시간이 가장 짧은 작업부터 실행하는 스케줄링. 평균 대기 시간이 가장 짧지만, 실행 시간을 미리 알기 어렵고 긴 작업이 굶주릴 수 있다.

Round Robin

모든 사용자가 바로 반응한다고 느끼게 하려면 CPU를 짧게 나눠 돌아가며 줘야 했다.
개념
정해진 시간(타임 슬라이스)씩 돌아가며 실행하는 선점형 스케줄링.

현대 운영체제는 우선순위와 섞어서 쓴다.

1960~90년대

Preemptive · Non-preemptive

시대적 배경
시분할 시스템은 1960년대부터 선점형을 썼다. PC에서는 윈도우 3.1 · 클래식 맥 OS의 비선점(협력형) 방식에서 윈도우 95 · NT, 맥 OS X로 오며 선점형이 됐다.
그래서 생긴 문제
비선점형에서는 프로그램 하나가 멈추면 시스템 전체가 멈췄다.
개념
실행 중인 프로세스의 CPU를 운영체제가 빼앗을 수 있으면 선점형, 스스로 내놓을 때까지 기다리면 비선점형.

파일 시스템

파일 시스템

1960~70년대

File system

시대적 배경
1960년대 Multics가 계층형 디렉터리를 도입했고, 1970년대 유닉스가 이를 단순하게 정리했다. PC에서는 1977년 FAT가 나와 MS-DOS(1981)에 쓰였다.
그래서 생긴 문제
디스크가 커지면서 사용자가 블록 번호로 데이터를 찾고 관리할 수 없게 됐다.
개념
디스크의 블록을 파일 · 디렉터리 단위로 이름 붙여 관리하는 운영체제의 구조.
지금은
Rocky Linux의 기본은 XFS, 많은 리눅스 배포판은 ext4를 쓴다.

관련 그림: 파일 시스템

디렉터리 계층

1960년대 · 1994

Directory hierarchy

시대적 배경
Multics의 계층형 디렉터리를 유닉스가 이어받았다. 리눅스 배포판마다 달랐던 파일 위치는 1994년 FSSTND, 이후 FHS(파일 시스템 계층 표준)로 정리됐다.
그래서 생긴 문제
파일이 많아지면 한 곳에 둘 수 없고, 배포판마다 설정 · 로그 위치가 다르면 관리가 어려웠다.
개념
루트(/)에서 시작하는 트리 구조로 파일을 정리하는 방식. /etc(설정) · /var/log(로그) · /home(사용자)처럼 용도별 위치가 정해져 있다.

관련 그림: 파일 시스템

inode

1970년대 초

Index node

시대적 배경
1970년대 초 켄 톰프슨과 데니스 리치가 만든 유닉스 파일 시스템에서 쓰였다. 흔히 index node의 줄임말로 설명된다.
그래서 생긴 문제
파일 이름과 파일 정보 · 블록 위치를 함께 두면, 하나의 파일에 여러 이름을 붙이거나 흩어진 블록을 찾기 어려웠다.
개념
파일의 메타데이터(권한 · 소유자 · 크기 · 시간 · 데이터 블록 위치)를 담는 구조. 파일 이름은 디렉터리에 따로 있다.
지금은
ls -li로 inode 번호를 볼 수 있다.

관련 그림: 파일 시스템

인덱스 할당

1970년대

Indexed allocation

시대적 배경
파일을 연속된 블록에 두는 연속 할당과 블록끼리 다음 위치를 이어 두는 연결 할당(FAT 등)의 단점을 보완하려고 유닉스 계열이 썼다.
그래서 생긴 문제
연속 할당은 빈 공간이 조각나고, 연결 할당은 중간 위치로 바로 가기 어려웠다.
개념
파일이 쓰는 블록들의 위치를 한 곳(inode)에 모아 두고, 그 목록으로 블록을 찾는 방식.

리눅스 관리

파일 권한 (rwx · 755)

1970년대

File permissions

시대적 배경
1970년대 초 유닉스가 여러 사용자가 한 컴퓨터를 나눠 쓰는 환경을 위해 도입했고, 리눅스가 그대로 이어받았다.
그래서 생긴 문제
다른 사용자의 파일을 함부로 읽거나 바꾸지 못하게 하면서도, 함께 쓸 파일은 공유해야 했다.
개념
소유자 · 그룹 · 기타 세 묶음에 읽기(r=4) · 쓰기(w=2) · 실행(x=1) 권한을 주는 방식. 755 = rwxr-xr-x.

umask

유닉스 시절

User file-creation mode mask

시대적 배경

그래서 생긴 문제
파일을 만들 때마다 chmod로 권한을 고치기는 번거롭고, 잊으면 보안 구멍이 됐다.
개념
새 파일 · 디렉터리를 만들 때 기본 권한(666 · 777)에서 꺼 둘 권한을 정하는 값. 022면 새 파일 644, 디렉터리 755.

systemd

2010

systemd

시대적 배경
1983년 유닉스 System V 이후 리눅스는 셸 스크립트를 순서대로 실행하는 SysV init을 오래 썼다. 2010년 레나르트 포터링 등이 systemd를 발표했고, 페도라 15(2011), RHEL 7(2014)부터 기본이 됐다.
그래서 생긴 문제
SysV init은 서비스를 하나씩 차례로 시작해 부팅이 느렸고, 서비스가 죽어도 감시하지 않았다.
개념
리눅스 부팅 후 첫 프로세스(PID 1)로 서비스를 병렬로 시작하고, 의존성 · 재시작 · 로그(journald)를 관리하는 시스템 관리자.

systemd가 관리할 서비스 · 타이머 등을 [Unit] · [Service] · [Install] 섹션으로 선언하는 설정 파일.

시대적 배경

dnf

2015

Dandified YUM

시대적 배경
rpm만 쓰던 시절에는 필요한 다른 패키지를 직접 찾아 설치해야 했다. 2003년 yum이 이를 자동화했고, 2015년 페도라 22에서 dnf가 yum을 대체했다. RHEL 8(2019) · Rocky Linux 8부터 쓰인다.
그래서 생긴 문제
의존성을 일일이 찾아 설치하는 의존성 지옥이 있었고, yum은 느리고 의존성 계산이 불안정했다.
개념
저장소에서 패키지를 찾아 의존성까지 해결해 설치하는 도구. 실제 설치는 rpm이 한다.
