한 줄 답

  • 상용 LLM에 데이터센터가 필요한 건 모델 한 벌을 돌려서가 아니라 수백만 명에게 동시에 서비스해서다. 규모는 모델 크기 × 동시 사용자 수 × 컨텍스트 길이로 정해진다
  • KV 캐시는 앞 토큰들의 계산 결과(Key · Value)를 GPU 메모리에 저장해 두고 다시 쓰는 것이다. 계산을 줄이는 대신 사용자마다 메모리를 수십 GB씩 쓸 수 있다

  • Whisper는 가중치가 MIT 라이선스로 공개돼 파인튜닝할 수 있다. 결과는 코드보다 데이터 품질과 평가셋 설계에서 갈린다
  • 개인정보 마스킹은 인식과 분리해서 후처리로 한다. 파인튜닝을 쓴다면 가린 결과가 아니라 태그를 붙여 출력하게 하고 정규식 안전망을 한 번 더 둔다

1. 상용 LLM은 왜 데이터센터가 필요한가

Q1.Claude · Gemini · GPT 같은 상용 LLM을 운영하려면 데이터센터 단위 인프라가 필요한가?

맞다. 다만 정확히는 "모델 한 벌을 돌리는 데"가 아니라 "수백만 명에게 동시에 서비스하는 데" 필요하다. 학습과 추론을 나눠 보면 분명해진다.

  • 학습: GPU(나 전용 가속기) 수천~수만 장을 고속 네트워크(InfiniBand 등)로 묶어 몇 주~몇 달 돌린다. 전력이 수십~수백 MW 단위라 처음부터 데이터센터 말고는 방법이 없다.
  • 추론: 프런티어 모델 한 벌은 보통 GPU 서버 1대(8 GPU)나 몇 대에 올라간다. 가중치가 수백 GB~TB 규모라 여러 GPU 메모리(HBM)에 나눠 싣는다(정확한 파라미터 수는 각 회사가 공개하지 않는다).
  • 병목은 연산보다 메모리다. 사용자마다 대화 맥락을 KV 캐시로 들고 있어야 해서, 컨텍스트가 긴 작업일수록 한 사람이 GPU 메모리를 많이 차지한다. 이런 서버를 동시 접속자 수에 맞춰 수천~수만 대 깔아야 하니 결국 데이터센터 규모가 된다.
흐름 2012년 AlexNet이 GPU 2장으로 학습되며 딥러닝이 GPU 위로 올라왔다. 2017년 트랜스포머, 2020년 GPT-3(파라미터 1,750억 개)로 모델이 커졌고, 2022년 ChatGPT 이후 서비스 이용자가 수억 명 단위가 됐다. 학습 클러스터도 커졌지만, 이용자가 폭증하면서 추론 인프라도 데이터센터 단위가 됐다.

작은 모델은 다르다. 7B~70B급 오픈 모델(Llama, Qwen 등)은 양자화하면 GPU 1장이나 서버 1대로 돌아간다. 고객사에 설치하는 온프레미스 STT도 같은 원리다. 모델이 작고 동시 처리 채널 수가 정해져 있으니 서버 몇 대로 충분하다.

그림 1. 학습은 처음부터 데이터센터 규모다. 추론은 "한 벌"은 서버 1대로 되지만, 사용자 수만큼 늘려야 해서 결국 데이터센터 규모가 된다

2. KV 캐시

Q2.KV 캐시는 무엇이고, 왜 메모리 문제가 되나?

LLM이 앞서 처리한 토큰들의 계산 결과(Key, Value)를 GPU 메모리에 저장해 두는 것이다. 다음 토큰을 만들 때 같은 계산을 처음부터 다시 하지 않으려고 쓰는 메모이제이션이다.

  • 트랜스포머는 토큰을 하나씩 생성하고, 새 토큰을 만들 때마다 어텐션으로 "앞의 모든 토큰"을 참조한다.
  • 각 토큰은 층마다 Query · Key · Value 벡터를 만든다. 새 토큰의 Query를 앞 토큰들의 Key와 비교해 가중치를 정하고, 그 가중치로 Value를 섞는다.
  • 앞 토큰의 K · V는 한 번 계산하면 바뀌지 않는다. 저장해 두면 매 단계 새 토큰 하나분만 계산하면 된다. 캐시가 없으면 매번 전체를 다시 계산해야 해서 생성이 극단적으로 느려진다.

그림 2. 캐시가 없으면 계산량이 단어 수의 제곱으로 늘어난다. KV 캐시는 계산을 줄이는 대신 메모리를 쓴다

문제는 크기다. 크기 공식은 2(K, V) × 레이어 수 × KV 헤드 수 × 헤드 차원 × 바이트 수 × 토큰 수다. Llama 3 70B(FP16)로 계산하면 토큰 1개당 약 320KB, 128K 토큰 컨텍스트면 사용자 1명당 약 40GB다. 모델 가중치와 별도로, 사용자 한 명이 긴 대화를 하면 GPU 메모리를 수십 GB씩 차지한다는 뜻이다.

그림 3. 앞에서 "병목은 메모리"라고 한 이유. 연산 속도와 메모리를 맞바꾸는 구조다

줄이는 기법

  • GQA · MQA: 여러 Query 헤드가 K · V를 공유해 캐시를 줄인다(위 계산의 "KV 헤드 8개"가 이것).
  • KV 캐시 양자화: FP16 대신 FP8 · INT4로 저장한다.
  • PagedAttention(vLLM): 운영체제의 페이징처럼 캐시를 블록 단위로 관리해 낭비를 줄인다.
  • 프롬프트 캐싱: 같은 시스템 프롬프트의 KV를 여러 요청이 재사용한다. API의 "캐시 히트 할인"이 이것이다.

3. 학습과 파인튜닝

Q3.파인튜닝이 뭐지? 먼저 "학습"이 뭔가?

모델은 결국 거대한 숫자 묶음(가중치)이다. Whisper large는 이런 숫자가 약 15억 개다. 학습은 이 숫자들을 조정하는 과정이다. 입력을 넣어 출력을 만들고, 정답과 비교해 얼마나 틀렸는지(loss) 계산하고, 틀린 정도를 줄이는 방향으로 숫자를 조금씩 고친다(역전파 · 경사하강법). 이걸 수십만~수백만 번 반복한다.

그림 4. 학습 루프. 사전학습이든 파인튜닝이든 이 루프는 똑같다

Q4.사전학습과 파인튜닝은 무엇이 다른가?

  • 사전학습: 무작위 숫자에서 시작해 방대한 데이터로 학습한다. OpenAI가 Whisper를 약 68만 시간 분량으로 학습시킨 게 이것이다.
  • 파인튜닝: 그렇게 완성된 숫자에서 시작해 적은 데이터(예: 100시간)로, 작은 학습률로 살짝만 조정한다.

알고리즘은 똑같다. 출발점과 데이터 규모가 다를 뿐이다. 일반 속기를 이미 잘하는 속기사가 특정 회사 콜센터의 용어와 말투에 적응하는 것과 비슷하다. 처음부터 한글을 가르치는 게 아니다.

그림 5. 내가 할 수 있는 건 아래 두 줄이다. 프롬프트(initial_prompt)나 RAG는 가중치를 바꾸지 않으므로 파인튜닝이 아니다

냉정하게: 파인튜닝은 "말투 · 형식 · 특정 작업"을 가르치는 데 효과적이고, "새 지식 주입"에는 효율이 낮다. 사내 문서 기반 Q&A가 목적이라면 RAG가 먼저다.

4. 파인튜닝 방식과 GPU 메모리

Q5.Qwen 같은 모델을 학습할 때 필요한 것은?

"학습"이 무엇을 뜻하느냐에 따라 완전히 다르다.

  • 사전학습(알리바바가 한 것): Qwen2.5는 사전학습 데이터를 7조 토큰에서 18조 토큰으로 늘렸고, Qwen3는 약 36조 토큰으로 알려져 있다. GPU 수천 장 이상으로 몇 주~몇 달 돌린다(정확한 규모는 공개하지 않음). 사전학습 → 긴 컨텍스트 확장 → 사후학습(SFT, 선호도 학습 · RL) 순서다.
  • 파인튜닝(직접 할 수 있는 것): 공개된 가중치를 받아 내 데이터로 추가 학습한다. 필요한 GPU 메모리가 방식에 따라 크게 다르다.

풀 파인튜닝은 왜 파라미터당 16바이트인가: 혼합 정밀도 + Adam 기준으로 가중치(FP16) 2 + 기울기(FP16) 2 + 가중치의 FP32 사본 4 + Adam 상태 2개(FP32) 8 = 16바이트다. 여기에 배치 크기에 따라 활성값이 더해진다.

그림 6. 풀 파인튜닝 메모리의 절반이 옵티마이저(Adam) 상태다. LoRA는 학습하는 가중치가 적어 이 부분이 거의 사라진다

GPU 48GB 한 장(RTX A6000급)으로 되는 것

  • Whisper: small · medium · large-v3-turbo는 풀 파인튜닝까지 여유 있게 된다. large-v3(1.55B)도 그래디언트 체크포인팅을 켜면 풀 파인튜닝이 된다. Ampere 세대라 BF16을 쓴다.
  • LLM: 7B~14B LoRA, 32B QLoRA까지 가능하다. 7B 풀 파인튜닝(112GB 이상)과 70B급은 안 된다.
  • 24GB 소비자용 GPU(RTX 3090 · 4090)로도 Whisper medium 풀 파인튜닝과 7B QLoRA까지 해 볼 수 있다.

데이터: 질문-답변 형식의 지시 데이터. 양보다 질이 중요해서 잘 만든 수백~수천 건으로도 효과가 난다. 도구: Hugging Face Transformers + PEFT + TRL, 또는 Unsloth, LLaMA-Factory.

5. Whisper 파인튜닝

Q6.STT 위스퍼는 훈련이 가능한가? 어떻게 하나?

가능하다. 가중치가 MIT 라이선스로 공개돼 있어 파인튜닝해서 상업적으로 써도 된다. 처음부터 사전학습하는 게 아니라 공개 모델에 내 데이터를 추가로 학습시키는 방식이다.

  • small(244M): 16GB GPU 한 장으로 풀 파인튜닝. 첫 실험용
  • medium(769M): 24GB면 풀 파인튜닝
  • large-v3(1.55B): 풀 파인튜닝은 40GB 이상, LoRA면 24GB
  • large-v3-turbo(809M): 디코더를 4층으로 줄인 버전이라 학습과 추론 모두 가볍다

Whisper는 오디오를 로그 멜 스펙트로그램으로 바꿔 인코더에 넣고, 디코더가 글자 토큰을 하나씩 만든다. 학습할 때는 디코더 출력을 정답 토큰과 비교하는데, 길이를 맞추려 채운 패딩은 라벨 마스킹(-100)으로 채점에서 뺀다.

그림 7. Whisper도 디코더가 토큰을 하나씩 만드는 트랜스포머라 KV 캐시를 쓴다. 학습 데이터는 반드시 30초 이하 구간과 그 구간의 전사 쌍이어야 한다

순서

  • 데이터 준비(시간이 가장 많이 드는 단계): CSV를 path,text 두 컬럼으로 만들고 학습용 · 평가용을 따로 둔다. 오디오는 30초 이하로 자른다. 전사 규칙(숫자를 "3만원"으로 쓸지 "삼만 원"으로 쓸지, 간투사 포함 여부)을 하나로 통일한다. 규칙이 섞이면 모델도 섞여서 배운다.
  • 환경: pip install torch transformers accelerate evaluate jiwer librosa soundfile pandas datasets. 첫 실험은 whisper-small로, 메모리가 부족하면 배치를 줄이고 누적 횟수(accum)를 늘린다.
  • 실행: train_whisper.py는 학습 전에 베이스라인 CER을 먼저 출력한다. 학습이 끝난 뒤 그 숫자보다 내려가야 의미가 있다.
  • 결과 판단: 평가 CER은 내려가는데 일반 발화가 나빠졌다면 망각이다(일반 데이터를 섞어 재학습). 학습 loss는 내려가는데 평가 CER이 오르면 과적합이다(step 수를 줄임).
  • 배포: faster-whisper(CTranslate2)로 변환해서 쓴다.
python train_whisper.py --train train.csv --eval eval.csv --model openai/whisper-small --out ./whisper-ko

ct2-transformers-converter --model ./whisper-ko --output_dir whisper-ko-ct2 \
  --copy_files tokenizer.json preprocessor_config.json --quantization float16

실무에서 주의할 점

  • 평가는 CER로: 한국어는 띄어쓰기 때문에 WER이 왜곡된다.
  • 망각: 좁은 도메인 데이터로만 학습하면 일반 발화 인식률이 떨어진다. 일반 데이터를 섞는다.
  • 환각: 무음 · 잡음 구간에서 없는 문장을 지어내는 문제는 파인튜닝만으로 잘 안 고쳐진다. VAD로 앞단에서 거른다.
  • 용어만 문제라면 학습 전에 initial_prompt에 전문 용어를 넣어 본다. 비용이 0이다.
  • 8kHz 전화 녹취는 Whisper 학습 데이터와 특성이 달라 성능이 떨어진다. 콜센터용이면 8kHz 데이터로 파인튜닝하는 효과가 가장 크다.
  • GPU 서버에서 돌릴 때: 운영 · 시연용 서버라면 학습이 GPU를 거의 독점하므로 야간 · 주말에 돌리거나 전용으로 뺀다. nvidia-smi로 메모리 · 드라이버 · CUDA 버전을 확인하고, 처음엔 짧게 돌리며 nvidia-smi -l 5로 온도와 전력을 지켜본다. 기존 서비스와 환경이 섞이지 않게 가상환경이나 컨테이너로 분리한다.

처음부터 100시간 전체 + large로 돌렸다가 하루 뒤에 설정 실수를 발견하는 게 가장 흔한 시간 낭비다. small + 몇 시간 분량으로 끝까지 도는지 → 베이스라인 대비 CER이 내려가는지 → 전체 데이터와 large 순서로 간다.

6. 100시간 속기록으로 학습 데이터 만들기

Q7.실제 녹취 100시간과 속기록을 파인튜닝 데이터로 쓰려면?

핵심 문제는 녹취는 길고 속기록은 시간 정보 없이 통으로 되어 있다는 점이다. Whisper는 30초 이하 구간과 그 구간의 텍스트 쌍이 필요하니, 일의 대부분은 속기록 문장을 오디오 시간에 맞춰 붙이고(강제 정렬) 자르는 것이다.

그림 8. 인식이 틀려도 대부분의 글자는 맞기 때문에, Whisper 인식 결과를 정렬의 기준점으로 쓸 수 있다

  • 속기록 상태부터 확인: 문장별 타임스탬프가 있으면 그 시간대로 자르면 되니 ②~③은 건너뛴다. 그리고 속기록은 녹취를 그대로 받아 적은 글이 아니다. 간투사를 빼고, 문법을 다듬고, "(웃음)" 같은 주석을 넣는 경우가 많다. 그대로 학습하면 모델이 "다듬어서 받아쓰기"를 배운다. 원하는 방향인지 먼저 정한다.
  • 텍스트 정리: 화자 표시 · 주석 · 머리말을 지우고 숫자 표기 · 간투사 처리 같은 전사 규칙을 통일한다.
  • 정렬: Whisper 인식 결과와 속기록을 글자 단위로 대조(difflib 같은 편집거리 정렬)해 속기록 글자마다 시간을 매핑하고, VAD로 찾은 쉼에서 자른다. WhisperX(한국어 wav2vec2 정렬 모델 지원)를 쓰는 방법도 있다.
  • 스테레오 녹취(상담원 · 고객 채널 분리)라면 채널부터 나눈다. 겹침 발화가 사라져 정렬이 훨씬 쉬워진다.
  • 품질 필터링: 구간별로 원본 Whisper 결과와 속기록의 CER을 계산해 너무 높은 구간(예: 50% 초과)은 버린다. 대부분 정렬이 틀어진 구간이다. 1초 미만 · 빈 텍스트 구간도 지운다.
  • 분할: 구간이 아니라 녹취 파일(통화) 단위로 나눈다. 같은 통화의 구간이 양쪽에 들어가면 화자와 내용이 겹쳐 평가 점수가 실제보다 좋게 나온다. 흔한 실수다.
  • 학습: 100시간이면 도메인 적응에 충분한 양이다. medium 풀 파인튜닝이나 large-v3-turbo + LoRA가 적당하다.

주의: 실제 고객 녹취는 개인정보 덩어리다. 학습 목적의 이용이 수집 동의 범위에 들어가는지, 비식별화가 필요한지 고객사와 먼저 확인한다. 기술보다 이쪽에서 막히는 경우가 많다.

7. 개인정보 마스킹

Q8.Whisper에서 텍스트 마스킹이 가능한가?

Whisper 자체에는 마스킹 기능이 없다. 카드번호 · 전화번호 · 이름을 가리는 개인정보 마스킹은 STT 결과에 후처리 단계를 붙여서 구현한다.

  • 정규화(ITN): "공일공 일이삼사"를 "010 1234"로 바꾼다. Whisper는 숫자를 숫자로도 한글로도 쓰기 때문에, 이 단계 없이 정규식을 걸면 놓치는 게 많다. 한국어 마스킹에서 가장 까다로운 부분이다.
  • 패턴 탐지: 카드번호 · 계좌 · 주민번호 · 전화번호처럼 형식이 정해진 건 정규식으로 잡는다.
  • NER 탐지: 이름 · 주소처럼 형식이 없는 건 한국어 NER 모델(KoELECTRA 계열 등)이나 LLM으로 찾는다.
  • 음성 마스킹: faster-whisper 등에서 word_timestamps=True를 켜면 단어마다 시작 · 끝 시간이 나온다. 그 구간을 묵음이나 삐 소리로 덮는다. 타임스탬프가 수백 ms씩 어긋날 수 있으니 앞뒤로 여유를 둔다.

Q9.파인튜닝에 마스킹 기능을 넣을 수는 없나?

가능하다. 다만 가린 결과(****)를 바로 출력하게 하는 대신, 개인정보 부분을 태그로 감싸서 출력하도록 학습시키는 게 낫다.

정답 전사(학습 데이터): 카드번호는 [[1234 5678 9012 3456]] 이고요
모델 출력:             카드번호는 [[1234 5678 9012 3456]] 이고요
후처리 결과:           카드번호는 **** 이고요

원문이 남아서 디버깅과 감사가 되고, 마스킹 규칙(전체를 가릴지, 뒤 4자리만 남길지)도 재학습 없이 후처리에서 바꿀 수 있다. 가린 결과를 바로 출력하게 학습시키면, 모델이 놓쳐도 알 방법이 없고 규칙이 바뀔 때마다 재학습해야 한다. 금융 · 공공 고객사라면 "왜 이게 가려졌고 저건 안 가려졌나"를 설명할 수 있어야 한다.

그림 9. 어느 쪽이든 마지막에 정규식 안전망을 둔다. 모델이 놓친 카드번호를 정규식이 잡는다

  • 데이터 라벨링: 기존 전사에 정규식과 NER을 돌려 [[ ]] 태그를 자동으로 붙이고 사람이 검수한다. 태그 누락이 섞이면 모델이 "가끔은 안 감싸도 된다"고 배우니 검수가 핵심이다.
  • 학습: 앞의 스크립트를 그대로 쓴다. CSV의 text에 태그가 들어갈 뿐이다. [[ ]]는 일반 문자라 토크나이저를 고칠 필요가 없다(<pii> 같은 스페셜 토큰을 추가하면 디코딩의 skip_special_tokens=True에 지워져 번거롭다).
  • 후처리: re.sub(r"\[\[.*?\]\]", "****", text)
  • 합성 데이터: 개인정보가 들어간 실제 녹취는 학습에 쓰기 어렵다. 가짜 카드번호 · 이름 · 주소로 문장을 만들고 TTS로 음성을 합성해 쓴다. 한국어 TTS를 직접 다루는 입장에서는 유리하다. 단, 합성음만으로 학습하면 실제 통화 음질에서 성능이 떨어지니 실제 녹취와 섞는다.
  • 평가 지표를 따로: CER이 좋아도 개인정보를 놓치면 사고다. "태그해야 할 구간 중 몇 %를 태그했나"(재현율)를 따로 잰다. 마스킹은 정밀도보다 재현율이 중요하다.
  • 부수 효과: 학습 데이터의 숫자를 "1234"처럼 아라비아 숫자로 통일해 두면 모델 출력도 그렇게 바뀌어 ITN 문제가 상당 부분 줄어든다. 파인튜닝의 실질적인 이득은 이쪽이 더 클 수 있다.

8. 핵심 정리와 공부 순서

핵심 정리

  • LLM 인프라 규모 = 모델 크기 × 동시 사용자 수 × 컨텍스트 길이. 병목은 대개 연산이 아니라 GPU 메모리다
  • KV 캐시는 계산을 메모리로 바꾸는 메모이제이션이다. 그래디언트 체크포인팅은 반대로 메모리를 계산으로 바꾼다
  • 학습 = 순전파 → 손실 → 역전파 → 경사하강의 반복. 사전학습과 파인튜닝은 출발점과 데이터 규모만 다르다
  • 풀 파인튜닝은 파라미터당 약 16바이트(절반이 Adam 상태). LoRA · QLoRA는 학습 대상을 줄여 GPU 1장으로 가능하게 한다
  • Whisper 파인튜닝의 성패는 데이터(30초 이하 정렬 · 전사 규칙 통일 · 파일 단위 분할)와 베이스라인 대비 CER에서 갈린다
  • 개인정보 마스킹은 인식과 분리하고, 파인튜닝은 태그 출력 + 정규식 안전망 + 재현율 측정으로 쓴다

냉정한 조언 · 공부 순서

이 페이지의 개념 없이 스크립트나 데이터 준비만 따라가면 "돌리긴 했는데 왜 안 되는지 모르는" 상태가 된다. 손실 · 경사하강법 · 역전파 · 학습률 · 과적합을 먼저 잡고 → 어텐션(Q · K · V) → KV 캐시 → 학습 시 메모리 구성(기울기 · 옵티마이저 상태) 순서로 가면, 그림 6의 메모리 수치를 직접 계산할 수 있게 된다. 스크립트에서는 코드보다 collator에서 왜 -100으로 바꾸는지, 왜 CER을 쓰는지 같은 "이유" 쪽을 짚어 보는 게 남는다.
