LLM과 인프라

LLM (대규모 언어 모델)

2018~2020

Large Language Model

시대적 배경
2017년 트랜스포머가 나온 뒤, 모델을 키우고 데이터를 늘릴수록 성능이 계속 오른다는 것이 확인됐다(GPT-2 2019, GPT-3 2020 · 파라미터 1,750억 개).
그래서 생긴 문제
그 전의 언어 모델은 번역, 요약, 분류처럼 작업마다 따로 만들고 따로 학습시켜야 했다.
개념 · 역할
수십억~수조 개의 파라미터를 가진 트랜스포머 모델에 방대한 글을 학습시켜, 다음 토큰을 예측하는 방식으로 글을 이해하고 만들어 내는 모델. Claude, GPT, Gemini, Qwen이 모두 여기에 속한다.
헷갈리기 쉬운 점
언어를 이해하는 것처럼 보이지만 내부 동작은 '다음에 올 토큰의 확률'을 계산하는 것이다. 그래서 그럴듯하지만 틀린 답(환각)이 나올 수 있다.
지금 · 실무에서
상용 LLM은 API로 쓰고, Qwen 같은 오픈 모델은 가중치를 받아 사내 서버에서 직접 돌리거나 파인튜닝한다.

관련 그림: 상용 LLM과 데이터센터

트랜스포머

2017

Transformer

시대적 배경
2010년대 중반 번역 · 음성 인식은 RNN(LSTM)이 주류였다. RNN은 문장을 앞에서부터 한 단어씩 순서대로 처리한다.
그래서 생긴 문제
순서대로만 계산하니 GPU의 수천 개 코어를 동시에 쓰지 못해 학습이 느렸고, 문장이 길면 앞부분 정보가 흐려졌다.
개념 · 역할
2017년 구글 논문 "Attention Is All You Need"에서 나온 신경망 구조. 순서대로 처리하는 대신 어텐션으로 모든 단어 쌍의 관계를 한 번에 계산해 GPU 병렬 처리에 잘 맞는다.
헷갈리기 쉬운 점
학습할 때는 병렬이지만, 글을 '생성'할 때는 여전히 한 토큰씩 만든다. 그래서 생성 속도를 높이려고 KV 캐시가 필요하다.
지금 · 실무에서
LLM(GPT · Claude · Qwen)과 Whisper 모두 트랜스포머다. Whisper는 인코더와 디코더를 모두 쓰고, 대부분의 LLM은 디코더만 쓴다.

관련 그림: KV 캐시

파라미터 (가중치)

1958

Parameter · Weight

시대적 배경
1958년 로젠블랫의 퍼셉트론은 입력마다 '중요도 숫자'를 곱해 더하는 방식으로 판단했다. 이 숫자를 데이터에 맞게 고치는 것이 기계 학습의 출발점이었다.
그래서 생긴 문제
사람이 규칙을 직접 짜서는 음성 · 언어처럼 복잡한 문제를 다 표현할 수 없었다.
개념 · 역할
모델 안에 들어 있는, 학습으로 조정되는 숫자들. Whisper large는 약 15억 개, Qwen 7B는 약 70억 개다. 모델 파일의 대부분이 이 숫자다.
헷갈리기 쉬운 점
"7B"의 B는 billion(10억)이다. 숫자 하나가 FP16이면 2바이트이므로 7B 모델은 가중치만 약 14GB다.
지금 · 실무에서
모델을 GPU에 올린다는 건 이 숫자들을 GPU 메모리에 싣는다는 뜻이다. 그래서 파라미터 수가 필요한 GPU 메모리를 결정한다.

관련 그림: 학습과 파인튜닝

GPU · GPU 메모리 (VRAM · HBM)

2007~2013

GPU · VRAM · HBM

시대적 배경
GPU는 게임 화면의 수많은 점을 동시에 계산하려고 만든 칩이다. 2007년 NVIDIA CUDA로 일반 계산에도 쓸 수 있게 됐고, 2012년 AlexNet이 GPU로 딥러닝을 학습시키면서 AI의 표준 장비가 됐다. 고대역폭 메모리 HBM은 2013년 표준이 됐다.
그래서 생긴 문제
신경망 계산은 거대한 행렬 곱셈의 반복인데, CPU는 코어가 수십 개라 동시에 처리할 수 있는 양이 적었다.
개념 · 역할
수천 개의 작은 코어로 같은 계산을 동시에 하는 칩. GPU에 붙은 전용 메모리(VRAM)에 모델 가중치와 KV 캐시가 올라가며, 데이터센터용 GPU는 대역폭이 매우 높은 HBM을 쓴다.
헷갈리기 쉬운 점
LLM 추론의 병목은 계산 속도보다 메모리 용량과 대역폭인 경우가 많다. 코어가 빨라도 가중치를 메모리에서 읽어 오는 속도가 따라오지 못한다.
지금 · 실무에서
RTX A6000은 GDDR6 48GB, 데이터센터용 H100은 HBM 80GB다. 어떤 모델을 돌릴 수 있는지는 거의 VRAM 크기로 결정된다.

관련 그림: 상용 LLM과 데이터센터

학습 · 추론

2012~

Training · Inference

시대적 배경
딥러닝이 GPU로 대형화되면서, 모델을 '만드는 일'과 '쓰는 일'은 필요한 자원도, 하는 곳도 완전히 달라졌다.
그래서 생긴 문제
둘을 구분하지 않으면 "LLM을 돌리려면 데이터센터가 필요하다" 같은 말을 정확히 이해할 수 없다.
개념 · 역할
학습은 데이터로 가중치를 조정하는 단계, 추론은 완성된 가중치로 입력에 대한 출력을 계산하는 단계다. 학습에는 기울기와 옵티마이저 상태까지 메모리가 더 들고, 추론에는 사용자 수만큼 KV 캐시가 든다.
헷갈리기 쉬운 점
파인튜닝도 '학습'이다. 반면 프롬프트나 RAG로 답을 바꾸는 건 가중치를 바꾸지 않으므로 추론이다.
지금 · 실무에서
고객사에 설치하는 STT 서버는 추론 서버다. 파인튜닝은 별도 GPU 서버에서 하고, 결과 가중치만 추론 서버에 배포하는 게 일반적이다.

관련 그림: 상용 LLM과 데이터센터

어텐션과 KV 캐시

토큰

2016

Token

시대적 배경
신경망은 글자가 아니라 숫자만 다룬다. 2016년 무렵 번역 모델에 BPE(자주 붙어 나오는 글자 조각을 하나로 묶는 방법)가 도입되면서 지금의 토큰 방식이 자리 잡았다.
그래서 생긴 문제
단어 단위로 자르면 사전에 없는 새 단어를 처리하지 못하고, 글자 단위로 자르면 문장이 너무 길어진다.
개념 · 역할
모델이 글을 처리하는 기본 단위. 단어보다 작고 글자보다 큰 조각이며, 각 토큰은 번호(ID)로 바뀌어 모델에 들어간다. Qwen은 약 15만 개, Whisper는 약 5만 개의 토큰 사전을 쓴다.
헷갈리기 쉬운 점
토큰 수와 글자 수는 다르다. 한국어는 영어보다 같은 내용에 토큰이 더 많이 드는 편이라 컨텍스트와 API 비용 계산에서 차이가 난다.
지금 · 실무에서
컨텍스트 길이, KV 캐시 크기, API 요금, Whisper의 라벨 길이 제한(448토큰)이 모두 토큰 단위로 계산된다.

관련 그림: KV 캐시

어텐션 (Q · K · V)

2014~2017

Attention · Query · Key · Value

시대적 배경
2014년 번역 모델에서 "출력 단어를 만들 때 입력 문장의 어느 부분을 볼지"를 계산하는 어텐션이 나왔고, 2017년 트랜스포머가 이것을 Query · Key · Value 형태로 일반화했다.
그래서 생긴 문제
문장 전체를 고정된 크기의 숫자 묶음 하나로 압축해 넘기던 방식은, 문장이 길어질수록 앞쪽 정보가 사라졌다.
개념 · 역할
각 토큰이 Query(내가 찾는 것) · Key(나를 찾을 때 쓰는 표지) · Value(내가 가진 정보)를 만든다. 새 토큰의 Query를 앞 토큰들의 Key와 비교해 점수를 내고, 그 점수로 Value를 가중 평균해 다음 계산에 쓴다.
헷갈리기 쉬운 점
모든 토큰 쌍을 비교하므로 계산량이 길이의 제곱으로 늘어난다. 컨텍스트가 2배면 어텐션 계산은 약 4배다.
지금 · 실무에서
Q · K · V를 알아야 KV 캐시, GQA, 컨텍스트 길이에 따른 메모리 문제가 이해된다.

관련 그림: KV 캐시

KV 캐시

2017~

KV Cache

시대적 배경
트랜스포머로 글을 생성하면 토큰을 하나 만들 때마다 앞의 모든 토큰을 어텐션으로 다시 참조해야 한다.
그래서 생긴 문제
매번 앞 토큰들의 Key · Value를 처음부터 다시 계산하면, 글이 길어질수록 같은 계산이 끝없이 반복되어 생성이 극단적으로 느려진다.
개념 · 역할
앞서 처리한 토큰들의 Key · Value 벡터를 GPU 메모리에 저장해 두고 재사용하는 것. 계산을 줄이는 대신 메모리를 쓴다(메모이제이션).
헷갈리기 쉬운 점
모델 가중치와 별개로 '사용자마다' 쌓인다. Llama 3 70B 기준 토큰당 약 320KB, 128K 토큰이면 사용자 1명에 약 40GB다.
지금 · 실무에서
동시 사용자 수와 컨텍스트 길이가 늘면 KV 캐시가 GPU 메모리를 먼저 채운다. 상용 LLM 서비스에 서버가 그렇게 많이 필요한 이유다.

관련 그림: KV 캐시

컨텍스트 길이

2017~2024

Context Length · Context Window

시대적 배경
초기 트랜스포머 모델은 한 번에 512토큰 정도만 볼 수 있었다. 2023~2024년 사이 10만~100만 토큰을 받는 모델이 나왔다.
그래서 생긴 문제
긴 문서, 긴 대화, 큰 코드베이스를 한 번에 넣지 못해 잘라서 따로 처리해야 했다.
개념 · 역할
모델이 한 번에 입력으로 받아 참조할 수 있는 최대 토큰 수. 질문, 대화 기록, 첨부 문서, 생성 중인 답이 모두 여기에 들어간다.
헷갈리기 쉬운 점
한도가 크다고 공짜가 아니다. 길이에 비례해 KV 캐시 메모리가, 길이의 제곱에 비례해 어텐션 계산이 늘어난다.
지금 · 실무에서
Claude Code처럼 파일을 많이 읽는 작업은 컨텍스트를 크게 쓰므로, 사용자 1명이 GPU 메모리를 많이 차지한다.

관련 그림: KV 캐시

GQA · MQA

2019~2023

Grouped-Query / Multi-Query Attention

시대적 배경
2019년 MQA, 2023년 GQA가 제안됐다. 모델이 커지고 컨텍스트가 길어지면서 KV 캐시가 메모리를 너무 많이 차지했기 때문이다.
그래서 생긴 문제
어텐션 헤드마다 K · V를 따로 저장하면, 헤드가 64개인 모델은 KV 캐시도 64벌이 필요했다.
개념 · 역할
여러 Query 헤드가 하나의 K · V 헤드를 공유하게 해서 KV 캐시 크기를 줄이는 방법. MQA는 전부가 1벌을 공유하고, GQA는 몇 개 그룹으로 나눠 공유한다.
헷갈리기 쉬운 점
줄일수록 메모리는 아끼지만 품질이 조금 떨어질 수 있다. GQA는 그 사이의 절충이다.
지금 · 실무에서
Llama 3 70B는 Query 헤드 64개, KV 헤드 8개인 GQA다. KV 캐시 계산식의 'KV 헤드 수'가 이 값이다.

관련 그림: KV 캐시

PagedAttention (vLLM)

2023

PagedAttention

시대적 배경
2023년 UC 버클리 연구진이 vLLM과 함께 발표했다. 운영체제가 메모리를 페이지 단위로 관리하는 방식(가상 메모리)을 KV 캐시에 그대로 가져왔다.
그래서 생긴 문제
사용자마다 '최대 길이만큼' KV 캐시 공간을 연속으로 미리 잡아 두니, 실제로는 짧게 끝나는 대화가 많아 메모리 대부분이 빈 채로 낭비됐다.
개념 · 역할
KV 캐시를 고정 크기 블록으로 나눠, 토큰이 늘어날 때마다 블록을 하나씩 할당하고 표로 위치를 관리하는 기법. 같은 GPU로 동시에 처리하는 요청 수가 크게 늘어난다.
헷갈리기 쉬운 점
모델 자체를 바꾸는 기술이 아니라 '서빙 엔진'의 메모리 관리 기술이다. 결과는 같고 처리량만 늘어난다.
지금 · 실무에서
STAGE 1에서 배운 MMU · 페이징과 같은 원리다. 오픈 모델을 직접 서비스할 때 vLLM 같은 서빙 엔진을 쓴다.

관련 그림: KV 캐시

프롬프트 캐싱

2024

Prompt Caching

시대적 배경
2024년 무렵 주요 LLM API들이 도입했다. 시스템 프롬프트, 긴 문서처럼 요청마다 똑같이 앞에 붙는 내용이 점점 길어졌기 때문이다.
그래서 생긴 문제
앞부분이 같은데도 요청이 올 때마다 그 부분의 KV 캐시를 처음부터 다시 계산해 시간과 비용이 반복됐다.
개념 · 역할
여러 요청에 공통으로 들어가는 앞부분(프롬프트 접두부)의 KV 캐시를 저장해 두고 다음 요청에서 재사용하는 것.
헷갈리기 쉬운 점
앞부분이 '완전히 똑같아야' 재사용된다. 중간에 날짜 같은 값이 바뀌면 그 뒤는 다시 계산된다.
지금 · 실무에서
API 요금표의 '캐시 읽기(cache hit) 할인'이 이것이다. 공통 지침은 프롬프트 맨 앞에 고정해 두는 게 유리하다.

관련 그림: KV 캐시

양자화

2022~

Quantization

시대적 배경
숫자를 적은 비트로 나타내는 기법은 오래됐지만, 2022년 LLM.int8(), GPTQ 같은 연구로 거대 언어 모델에도 품질 손실을 적게 하며 적용할 수 있게 됐다.
그래서 생긴 문제
70B 모델은 FP16 가중치만 140GB라 GPU 한두 장에 올라가지 않았다.
개념 · 역할
가중치(나 KV 캐시)를 16비트 대신 8비트, 4비트처럼 더 적은 비트로 저장해 메모리와 대역폭을 줄이는 기법.
헷갈리기 쉬운 점
비트를 줄일수록 정확도가 떨어질 수 있다. 특히 숫자 계산, 긴 추론에서 차이가 드러나므로 반드시 평가해 봐야 한다.
지금 · 실무에서
오픈 모델을 작은 GPU에서 돌릴 때(GGUF, AWQ, GPTQ), 그리고 QLoRA 파인튜닝에서 쓴다.

학습의 원리

손실 (loss)

1805

Loss Function

시대적 배경
1805년 르장드르가 관측값과 예측값 차이의 제곱합을 가장 작게 만드는 최소제곱법을 발표했다. '얼마나 틀렸는지를 숫자로 재고 그걸 줄인다'는 생각의 출발점이다.
그래서 생긴 문제
모델 출력이 좋은지 나쁜지를 숫자로 재지 못하면, 가중치를 어느 방향으로 고쳐야 할지 정할 수 없다.
개념 · 역할
모델의 출력이 정답과 얼마나 다른지를 숫자 하나로 나타낸 값. 학습은 이 값을 줄이는 과정이다. 언어 모델과 Whisper는 정답 토큰에 낮은 확률을 줄수록 커지는 교차 엔트로피 손실을 쓴다.
헷갈리기 쉬운 점
학습 loss가 내려간다고 실제 성능이 좋아진 것은 아니다. 평가셋의 지표(CER 등)를 따로 봐야 과적합을 잡을 수 있다.
지금 · 실무에서
학습 로그의 loss 그래프가 꾸준히 내려가는지, 갑자기 튀는지(학습률 과다)를 보는 것이 학습 상태 점검의 기본이다.

경사하강법 · 학습률

1847

Gradient Descent · Learning Rate

시대적 배경
1847년 코시가 함수의 값이 가장 빨리 줄어드는 방향(기울기의 반대 방향)으로 조금씩 이동하는 방법을 제안했다.
그래서 생긴 문제
가중치가 수십억 개이면 가능한 조합을 전부 시험해 손실이 가장 작은 값을 찾는 것은 불가능하다.
개념 · 역할
손실을 각 가중치로 미분한 기울기(gradient)를 구하고, 그 반대 방향으로 조금씩 가중치를 고치는 방법. 한 번에 얼마나 고칠지 정하는 보폭이 학습률이다.
헷갈리기 쉬운 점
학습률이 너무 크면 손실이 튀거나 발산하고, 너무 작으면 학습이 끝나지 않는다. 파인튜닝은 이미 좋은 지점에서 시작하므로 사전학습보다 훨씬 작은 학습률(예: 1e-5)을 쓴다.
지금 · 실무에서
학습 스크립트의 learning_rate와 warmup_steps(처음엔 작게 시작해 서서히 올림)가 이것을 정한다.

역전파

1986

Backpropagation

시대적 배경
1986년 러멜하트 · 힌턴 · 윌리엄스의 논문으로 널리 알려졌다(원리는 1970년대에 먼저 나왔다). 여러 층으로 된 신경망을 실제로 학습시킬 수 있게 한 방법이다.
그래서 생긴 문제
층이 수십~수백 개인 신경망에서 맨 앞쪽 가중치 하나가 최종 손실에 얼마나 영향을 주는지 일일이 재면 너무 오래 걸린다.
개념 · 역할
미분의 연쇄 법칙을 이용해, 손실에서 출발해 출력층에서 입력층 방향으로 거꾸로 계산하며 모든 가중치의 기울기를 한 번에 구하는 방법.
헷갈리기 쉬운 점
역전파를 하려면 순전파 때의 중간 계산값(활성값)을 메모리에 들고 있어야 한다. 학습이 추론보다 메모리를 훨씬 많이 쓰는 이유 중 하나다.
지금 · 실무에서
PyTorch의 loss.backward()가 역전파다. 직접 짤 일은 드물지만, 메모리 부족 오류를 이해하려면 알아야 한다.

관련 그림: 학습과 파인튜닝

옵티마이저 (Adam)

2014

Optimizer · Adam

시대적 배경
2014년 킹마와 바가 발표했다. 단순 경사하강법은 가중치마다 알맞은 보폭이 달라 학습이 불안정했다.
그래서 생긴 문제
모든 가중치에 같은 학습률을 쓰면, 어떤 가중치는 너무 크게, 어떤 가중치는 거의 움직이지 않았다.
개념 · 역할
기울기를 받아 실제로 가중치를 어떻게 고칠지 정하는 알고리즘. Adam(AdamW)은 가중치마다 기울기의 이동 평균과 기울기 제곱의 이동 평균, 두 값을 저장해 보폭을 자동 조절한다.
헷갈리기 쉬운 점
이 두 값은 가중치 하나당 FP32로 각 4바이트, 합쳐 8바이트다. 풀 파인튜닝 메모리(파라미터당 약 16바이트)의 절반이 옵티마이저 상태다.
지금 · 실무에서
LoRA가 메모리를 크게 줄이는 이유는, 학습하는 가중치가 적으니 옵티마이저 상태도 그만큼만 필요하기 때문이다.

과적합

통계학부터

Overfitting

시대적 배경
통계학에서 데이터에 너무 꼭 맞춘 모델이 새 데이터에서 틀리는 현상은 오래전부터 알려져 있었다. 데이터가 적고 모델이 클수록 심해진다.
그래서 생긴 문제
학습 데이터 성적만 보고 "잘 된다"고 판단하면, 실제 고객 음성에서는 성능이 떨어지는 일이 생긴다.
개념 · 역할
모델이 학습 데이터의 일반적인 패턴 대신 개별 사례를 외워, 학습 데이터에서는 잘 맞지만 새 데이터에서는 성능이 떨어지는 현상.
헷갈리기 쉬운 점
학습 loss는 계속 내려가는데 평가 CER이 오르기 시작하면 과적합 신호다. 오래 학습할수록 좋은 게 아니다.
지금 · 실무에서
평가셋 지표가 가장 좋았던 체크포인트를 고르고(load_best_model_at_end), step 수나 epoch을 줄인다.

파인튜닝 기법

사전학습

2018

Pre-training

시대적 배경
2018년 ELMo · GPT · BERT가 "정답 없는 방대한 글로 먼저 일반 능력을 학습시킨 뒤, 작업별로 조금 더 학습시키는" 방식이 압도적으로 좋다는 것을 보였다.
그래서 생긴 문제
작업마다 정답이 달린 데이터를 대량으로 만들어 처음부터 학습시키는 건 비용이 너무 컸다.
개념 · 역할
무작위 가중치에서 시작해 방대한 데이터로 모델의 기본 능력을 만드는 첫 학습 단계. Whisper는 68만 시간 음성, Qwen2.5는 18조 토큰으로 사전학습됐다.
헷갈리기 쉬운 점
개인이나 중소기업이 할 수 있는 규모가 아니다. 실무에서 "모델을 학습시킨다"고 하면 거의 항상 파인튜닝을 말한다.
지금 · 실무에서
공개된 사전학습 모델(가중치)을 받아 쓰는 것이 출발점이다. 라이선스를 확인한다(Whisper는 MIT, Qwen은 대부분 Apache 2.0).

파인튜닝

2014~2018

Fine-tuning

시대적 배경
이미지 분야에서 2014년 무렵부터 사전학습된 모델을 가져와 다른 작업에 맞게 조금 더 학습시키는 전이 학습이 퍼졌고, 2018년 ULMFiT · BERT로 언어 분야에도 정착했다.
그래서 생긴 문제
범용 모델은 우리 회사 콜센터 용어, 8kHz 전화 음질, 원하는 출력 형식을 모른다.
개념 · 역할
사전학습이 끝난 모델의 가중치에서 출발해, 비교적 적은 양의 내 데이터로 추가 학습시켜 특정 용도에 맞추는 것. 알고리즘은 사전학습과 같고 출발점과 데이터 규모만 다르다.
헷갈리기 쉬운 점
말투 · 형식 · 특정 작업을 가르치는 데는 효과적이지만, 새로운 사실 지식을 넣는 데는 비효율적이다. 문서 기반 답변이 목적이면 RAG가 먼저다.
지금 · 실무에서
Whisper 도메인 적응, 출력 형식 통일(숫자 표기), 개인정보 태그 출력 같은 작업이 파인튜닝으로 잘 풀린다.

관련 그림: 학습과 파인튜닝

LoRA

2021

Low-Rank Adaptation

시대적 배경
2021년 마이크로소프트 연구진이 발표했다. 모델이 수십억 파라미터로 커지면서 풀 파인튜닝에 필요한 GPU 메모리와 저장 공간을 감당하기 어려워졌다.
그래서 생긴 문제
가중치 전체를 학습시키면 옵티마이저 상태까지 파라미터당 약 16바이트가 들고, 작업마다 모델 전체 사본을 따로 저장해야 했다.
개념 · 역할
원본 가중치는 고정하고, 각 층에 작은 행렬 두 개(A · B)를 붙여 그 곱만큼만 가중치가 바뀌도록 학습하는 방법. 학습 대상 파라미터가 원본의 1% 미만으로 줄어든다.
헷갈리기 쉬운 점
풀 파인튜닝보다 성능이 약간 낮을 수 있지만 대부분의 도메인 적응에서는 차이가 작다. 추론 때는 어댑터를 원본에 합쳐(merge) 속도 손해 없이 쓸 수 있다.
지금 · 실무에서
Hugging Face PEFT 라이브러리로 몇 줄이면 적용된다. 7B LLM이나 Whisper large를 24GB GPU에서 학습할 때 기본 선택지다.

관련 그림: 파인튜닝 방식과 GPU 메모리

QLoRA

2023

Quantized LoRA

시대적 배경
2023년 데트머스 등이 발표했다. LoRA를 써도 원본 가중치를 FP16으로 올려 두는 것만으로 큰 모델은 GPU에 다 들어가지 않았다.
그래서 생긴 문제
원본은 얼려 두고 학습하지 않는데도, 16비트로 올려 두느라 메모리 대부분을 차지했다.
개념 · 역할
원본 가중치를 4비트로 양자화해 GPU에 올리고, 그 위에 LoRA 어댑터를 붙여 학습하는 방법. LoRA보다 메모리를 다시 크게 줄인다.
헷갈리기 쉬운 점
4비트를 16비트로 바꾸는 계산이 끼어서 LoRA보다 학습이 느리다. 메모리가 충분하면 일반 LoRA가 낫다.
지금 · 실무에서
24GB GPU 한 장으로 14B~32B LLM을 실험할 때 쓴다. 48GB GPU라면 7B~14B는 일반 LoRA로 충분하다.

망각 (파국적 망각)

1989

Catastrophic Forgetting

시대적 배경
1989년 매클로스키와 코언이 신경망에 새 과제를 학습시키면 이전 과제를 급격히 잊는 현상을 보고했다.
그래서 생긴 문제
좁은 도메인 데이터로만 파인튜닝하면, 그 도메인은 좋아지지만 원래 잘하던 일반 능력이 무너진다.
개념 · 역할
신경망이 새 데이터로 학습하면서 기존에 학습한 능력을 크게 잃는 현상. 가중치 전체가 새 데이터에만 맞춰지기 때문이다.
헷갈리기 쉬운 점
도메인 평가셋만 보면 눈치채지 못한다. 일반 음성 평가셋도 함께 측정해야 드러난다.
지금 · 실무에서
일반 공개 데이터(예: AI Hub 일반 대화)를 일정 비율 섞는다. LoRA처럼 원본을 얼리는 방법도 망각을 줄인다.

관련 그림: Whisper 파인튜닝

혼합 정밀도 (FP16 · BF16)

2017~2020

Mixed Precision · FP16 · BF16

시대적 배경
2017년 NVIDIA 연구진이 16비트로 계산하되 중요한 값은 32비트로 유지하는 혼합 정밀도 학습을 발표했다. 구글이 만든 BF16은 2020년 NVIDIA Ampere 세대(A100 · RTX 30 · A6000)부터 지원됐다.
그래서 생긴 문제
32비트(FP32)로만 학습하면 메모리를 2배 쓰고 계산도 느렸다. FP16만 쓰면 표현 범위가 좁아 아주 작은 기울기가 0이 되면서 학습이 깨졌다.
개념 · 역할
순전파 · 역전파 계산은 16비트로 하고, 가중치의 원본 사본과 옵티마이저 상태는 32비트로 유지하는 학습 방식. BF16은 FP32와 같은 지수 범위를 가진 16비트 형식이라 FP16보다 안정적이다.
헷갈리기 쉬운 점
GPU가 BF16을 지원하는지 확인해야 한다. Ampere 이전 세대(V100, RTX 20 등)는 BF16 하드웨어 가속이 없어 FP16을 써야 한다.
지금 · 실무에서
A6000 같은 Ampere 이상 GPU에서는 학습 설정에 bf16=True를 쓴다.

관련 그림: 파인튜닝 방식과 GPU 메모리

그래디언트 체크포인팅

2016

Gradient Checkpointing

시대적 배경
2016년 천 등이 "중간값을 일부만 저장하고 필요할 때 다시 계산하면 메모리를 크게 줄일 수 있다"는 방법을 발표했다.
그래서 생긴 문제
역전파를 하려면 순전파의 모든 층 중간값(활성값)을 들고 있어야 해서, 배치와 길이가 커지면 메모리가 부족했다.
개념 · 역할
순전파 중간값을 일부 지점에만 저장하고, 역전파 때 필요한 나머지는 그 지점부터 다시 계산하는 기법. 메모리를 계산 시간과 맞바꾼다.
헷갈리기 쉬운 점
KV 캐시와 방향이 반대다. KV 캐시는 메모리를 써서 계산을 줄이고, 체크포인팅은 계산을 더 해서 메모리를 줄인다.
지금 · 실무에서
Whisper large 풀 파인튜닝을 48GB GPU에 올릴 때 켜야 하는 옵션(gradient_checkpointing=True)이다.

Whisper

2022

Whisper

시대적 배경
2022년 9월 OpenAI가 공개했다. 그 전의 음성 인식 모델은 정제된 데이터 수천 시간으로 학습해 잡음이나 다른 언어에 약했다.
그래서 생긴 문제
좋은 음성 인식기를 만들려면 정확한 전사가 달린 음성이 대량으로 필요했는데, 사람이 전사한 데이터는 비싸고 적었다.
개념 · 역할

무음이나 잡음 구간에서 없는 문장을 만들어 내는 환각이 알려져 있다. 8kHz 전화 음성은 학습 데이터와 성격이 달라 성능이 떨어진다.
지금 · 실무에서
가중치가 MIT 라이선스라 상업적으로 파인튜닝해 쓸 수 있다. 서비스 배포는 faster-whisper(CTranslate2)로 변환해 쓰는 것이 일반적이다.

샘플레이트 (8kHz · 16kHz)

1928~1949

Sample Rate

시대적 배경
나이퀴스트(1928)와 섀넌(1949)이 "소리를 디지털로 담으려면 가장 높은 주파수의 2배 이상 자주 측정해야 한다"는 표본화 정리를 정리했다. 전화는 음성 대역(약 3.4kHz까지)만 담으려고 8kHz를 표준으로 삼았다.
그래서 생긴 문제
같은 소리도 몇 번 측정했는지에 따라 데이터가 달라서, 모델이 학습한 샘플레이트와 다른 오디오를 넣으면 제대로 인식하지 못한다.
개념 · 역할
1초에 소리 크기를 몇 번 측정해 저장하는지를 나타내는 값. 16kHz는 1초에 16,000번 측정한다. 담을 수 있는 최고 주파수는 샘플레이트의 절반이다.
헷갈리기 쉬운 점
8kHz를 16kHz로 리샘플링해도 4kHz 이상의 소리가 새로 생기지 않는다. 그래서 전화 음성은 8kHz 데이터로 파인튜닝하는 효과가 크다.
지금 · 실무에서
Whisper는 16kHz 입력을 쓴다. 학습 스크립트의 librosa.load(sr=16000)이 리샘플링을 한다.

로그 멜 스펙트로그램

1937

Log-Mel Spectrogram

시대적 배경
1937년 스티븐스 등이 사람이 느끼는 음높이 간격은 실제 주파수 간격과 다르다는 것을 측정해 멜(mel) 척도를 만들었다. 사람은 낮은 소리는 잘 구분하고 높은 소리는 덜 구분한다.
그래서 생긴 문제
소리 파형 자체는 1초에 16,000개 숫자라 너무 길고, 어떤 주파수가 얼마나 있는지가 겉으로 드러나지 않는다.
개념 · 역할
오디오를 짧은 구간(10ms 간격)마다 주파수 분석하고, 사람 귀의 감각에 맞춘 멜 척도로 묶은 뒤 로그를 취한 2차원 표. Whisper의 입력 형식이다(80칸, large-v3는 128칸).
헷갈리기 쉬운 점
Whisper는 항상 30초(3000프레임) 단위로 받는다. 짧은 오디오는 뒤를 0으로 채우고, 긴 오디오는 잘라서 여러 번 넣어야 한다.
지금 · 실무에서
학습 스크립트의 feature_extractor가 이 변환을 한다. 직접 계산할 일은 거의 없지만 입력 길이 제한(30초)의 이유다.

인코더 · 디코더

2014

Encoder · Decoder

시대적 배경
2014년 번역 연구에서 "입력을 읽어 이해하는 부분"과 "출력을 하나씩 만들어 내는 부분"을 나눈 시퀀스-투-시퀀스(seq2seq) 구조가 나왔다.
그래서 생긴 문제
음성(수천 프레임)과 글자(수십 토큰)처럼 입력과 출력의 길이와 종류가 다르면, 하나의 구조로 바로 연결하기 어렵다.
개념 · 역할
인코더는 입력 전체를 읽어 의미 있는 표현으로 바꾸고, 디코더는 그 표현을 어텐션으로 참조하면서 출력 토큰을 하나씩 생성한다. Whisper가 이 구조다.
헷갈리기 쉬운 점
대부분의 LLM(GPT · Claude · Qwen)은 인코더 없이 디코더만 쓴다. 디코더는 토큰을 하나씩 만들므로 Whisper도 KV 캐시를 쓴다.
지금 · 실무에서
large-v3-turbo는 디코더 층을 32개에서 4개로 줄여 빠르게 만든 버전이다. 생성(디코더)이 속도의 병목이기 때문이다.

CER · WER

1980s~

Character / Word Error Rate

시대적 배경
1980년대 음성 인식 연구가 공개 경쟁 평가(미국 NIST 등) 체제로 가면서, 서로 다른 인식기를 같은 숫자로 비교할 기준이 필요했다.
그래서 생긴 문제
"잘 알아듣는다"는 느낌만으로는 모델끼리, 파인튜닝 전후를 비교할 수 없다. 또 한국어는 띄어쓰기가 사람마다 달라 단어 기준으로 재면 왜곡된다.
개념 · 역할
인식 결과를 정답과 비교해, 글자(CER) 또는 단어(WER)를 몇 개 바꾸고 · 지우고 · 끼워 넣어야 같아지는지 센 뒤 정답 길이로 나눈 값. 낮을수록 좋다.
헷갈리기 쉬운 점
숫자 표기("3만 원" vs "삼만 원") 같은 전사 규칙이 다르면 실제로는 맞게 들었어도 오류로 잡힌다. 비교 전에 표기를 정규화해야 한다.
지금 · 실무에서
파인튜닝 전 베이스라인 CER과 후의 CER을 같은 평가셋으로 비교해야 효과를 말할 수 있다.

VAD (음성 구간 검출)

1960s~

Voice Activity Detection

시대적 배경
1960년 무렵 대서양 해저 전화 케이블에서 사람이 말하지 않는 순간을 감지해 회선을 다른 통화에 나눠 주는 기술(TASI)이 쓰였다. 디지털 전화(VoIP)에서는 무음 구간을 보내지 않아 대역폭을 아낀다.
그래서 생긴 문제
음성 인식기에 무음 · 잡음 구간까지 넣으면 계산이 낭비되고, Whisper는 그 구간에서 없는 문장을 지어내기도 한다.
개념 · 역할
오디오에서 사람이 말하는 구간과 무음 · 잡음 구간을 구분하는 기술. STT 앞단에서 인식할 구간을 고르고, 긴 오디오를 자연스러운 쉼에서 자르는 데 쓴다.
헷갈리기 쉬운 점
너무 민감하면 잡음을 말로, 너무 둔하면 작은 말소리를 무음으로 판단한다. 콜센터 환경에 맞게 임계값을 조정해야 한다.
지금 · 실무에서
faster-whisper의 vad_filter 옵션(Silero VAD)이 대표적이다. 학습 데이터를 30초 이하로 자를 때도 VAD로 찾은 쉼을 기준으로 한다.

Hallucination

시대적 배경
대규모 생성 모델이 널리 쓰이면서, 입력에 없는 내용을 그럴듯하게 만들어 내는 문제가 주목받았다. Whisper도 공개 직후부터 무음 구간 환각이 보고됐다.
그래서 생긴 문제

헷갈리기 쉬운 점
파인튜닝만으로는 잘 사라지지 않는다. 무음 구간이 거의 없는 데이터로만 학습하면 오히려 심해질 수 있다.
지금 · 실무에서
STT 결과가 기록 · 증빙으로 쓰이는 금융 · 공공 고객사에서는 환각이 곧 사고다. VAD와 후처리를 반드시 둔다.

ITN (역 텍스트 정규화)

1990s~

Inverse Text Normalization

시대적 배경
음성 인식이 받아쓰기 · 콜센터에 상용화되면서, '들린 그대로'의 출력을 사람이 읽고 시스템이 처리하기 좋은 표기로 바꿀 필요가 생겼다.
그래서 생긴 문제
같은 숫자도 "공일공 일이삼사", "010 1234"처럼 제각각 나오면 검색 · 마스킹 · 통계가 어렵다.
개념 · 역할
음성 인식 결과의 말 표기(삼만 원, 공일공)를 글 표기(3만 원, 010)로 바꾸는 처리. 반대 방향(글 → 말)은 TTS에서 쓰는 텍스트 정규화(TN)다.
헷갈리기 쉬운 점
한국어 숫자는 한자어와 고유어가 섞이고 문맥에 따라 읽는 법이 달라 규칙만으로 완벽하기 어렵다("세 개", "삼 개월").
지금 · 실무에서
파인튜닝 데이터의 전사를 아라비아 숫자로 통일하면 모델 출력 자체가 그렇게 바뀌어 ITN 부담이 줄어든다.

강제 정렬

1990s~

Forced Alignment

시대적 배경
1990년대 HMM 기반 음성 인식에서, 이미 알고 있는 정답 문장이 오디오의 어느 시간에 해당하는지 맞추는 기법이 학습 데이터 구축에 쓰였다.
그래서 생긴 문제
속기록처럼 긴 녹취 전체의 텍스트만 있고 시간 정보가 없으면, 30초 이하 구간과 그 구간의 텍스트 쌍을 만들 수 없다.
개념 · 역할
오디오와 그 정답 텍스트가 주어졌을 때, 텍스트의 각 글자 · 단어가 오디오의 몇 초에 해당하는지 찾아내는 것. 인식이 아니라 '맞추기'라서 정답이 이미 있다는 점이 다르다.
헷갈리기 쉬운 점
속기록이 녹취를 다듬은 글이면(간투사 생략, 문장 정리) 대조가 어긋나는 구간이 생긴다. CER 필터로 그런 구간을 버려야 한다.
지금 · 실무에서
WhisperX(한국어 wav2vec2 정렬 모델 지원)를 쓰거나, Whisper 인식 결과와 속기록을 편집거리로 정렬해 시간을 옮겨 붙인다.

시대적 배경

헷갈리기 쉬운 점

지금 · 실무에서
100시간이면 학습 90시간, 평가 5~10시간 정도로 나누고, 파인튜닝 전 베이스라인을 같은 평가셋으로 먼저 잰다.

라벨 마스킹 (-100)

2017~

Label Masking · ignore_index

시대적 배경
여러 문장을 한 묶음(배치)으로 학습하면서, 길이가 다른 문장을 같은 길이로 맞춰야 했다. PyTorch는 손실 계산에서 값이 -100인 위치를 무시하는 것을 기본값으로 정했다.
그래서 생긴 문제
짧은 문장을 긴 문장 길이에 맞추려고 채운 패딩까지 손실에 넣으면, 모델이 '패딩을 출력하라'는 엉뚱한 것을 배운다.
개념 · 역할
학습 라벨에서 손실 계산에 넣지 않을 위치를 -100으로 바꿔 두는 관례. PyTorch 교차 엔트로피 손실의 ignore_index 기본값이 -100이다.
헷갈리기 쉬운 점
개인정보를 가리는 '마스킹'과 이름만 같고 전혀 다른 개념이다. 이건 학습 채점에서 빼는 표시다.
지금 · 실무에서
Whisper 학습 스크립트의 collator가 패딩 위치를 -100으로 바꾼다. 이 처리가 빠지면 학습은 돌지만 결과가 이상해진다.

2011년 개인정보 보호법 시행 이후, 금융 · 공공 기관은 녹취와 전사 결과에 담긴 개인정보를 보호할 의무가 커졌다.
그래서 생긴 문제
STT 결과를 저장 · 검색 · 분석하면 카드번호, 계좌, 주민번호, 이름이 그대로 노출된다.
개념 · 역할
텍스트(나 음성)에서 개인을 식별할 수 있는 정보를 찾아 가리는 처리. STT에서는 인식 → 정규화 → 탐지(정규식 · NER) → 치환 순서로 후처리하는 것이 표준이다.
헷갈리기 쉬운 점
인식과 마스킹을 한 모델에 합치면 누락을 검증하기 어렵다. "왜 이건 가려졌고 저건 안 가려졌나"를 설명할 수 있는 구조가 필요하다.
지금 · 실무에서
파인튜닝으로 개인정보 구간에 태그([[ ]])를 붙이게 하고, 그 뒤에 정규식 마스킹을 한 번 더 거는 이중 구조가 현실적이다.

관련 그림: 개인정보 마스킹

NER (개체명 인식)

1995

Named Entity Recognition

시대적 배경
1995년 미국 MUC-6 평가 대회에서 글 속의 사람 이름 · 기관 · 장소 · 날짜를 찾는 과제가 '개체명 인식'으로 정의됐다.
그래서 생긴 문제
카드번호처럼 형식이 정해진 정보는 정규식으로 찾을 수 있지만, 이름이나 주소는 정해진 형식이 없다.
개념 · 역할
문장에서 사람 이름, 기관, 장소, 날짜 같은 개체가 어디에 있고 무엇인지 찾아내는 기술. 지금은 BERT 계열 모델이나 LLM으로 한다.
헷갈리기 쉬운 점
STT 결과는 띄어쓰기 · 문장부호가 불완전하고 인식 오류도 섞여 있어, 깨끗한 글로 학습한 NER보다 성능이 낮다.
지금 · 실무에서
한국어 NER 모델(KoELECTRA 계열 등)이나 LLM으로 이름 · 주소를 찾고, 형식 있는 정보는 정규식으로 찾아 둘을 합친다.

관련 그림: 개인정보 마스킹

정규식

1951

Regular Expression

시대적 배경
1951년 수학자 클리니가 문자열 패턴을 나타내는 정규 언어를 정의했고, 1968년 켄 톰프슨이 이를 편집기(QED)에 넣으며 프로그래밍 도구가 됐다(이후 grep).
그래서 생긴 문제
"숫자 4개-숫자 4개-…" 같은 형식을 찾으려고 문자 하나씩 비교하는 코드를 매번 짜기는 번거롭고 실수가 잦았다.
개념 · 역할
문자열의 패턴(숫자 몇 개, 반복, 선택 등)을 짧은 표기로 나타내 찾기 · 검증 · 치환에 쓰는 언어.
헷갈리기 쉬운 점
형식이 흔들리면 놓친다. STT 결과의 "공일공"은 숫자 패턴에 걸리지 않으므로 ITN을 먼저 해야 한다.
지금 · 실무에서
카드 · 계좌 · 주민번호 · 전화번호 마스킹의 1차 도구이자, 모델이 놓친 것을 잡는 마지막 안전망이다.

관련 그림: 개인정보 마스킹

정밀도 · 재현율

1955

Precision · Recall

시대적 배경
1950년대 문헌 검색 연구에서 "찾아낸 것 중 맞는 비율"과 "찾아야 할 것 중 찾아낸 비율"을 따로 재기 시작했다.
그래서 생긴 문제
마스킹 성능을 정확도 하나로만 보면, 개인정보를 몇 개 놓쳐도 전체 글자 대비로는 높은 점수가 나온다.
개념 · 역할
정밀도는 모델이 '맞다'고 한 것 중 실제로 맞은 비율, 재현율은 실제로 맞는 것 중 모델이 찾아낸 비율이다. 하나를 올리면 다른 하나가 내려가는 경우가 많다.
헷갈리기 쉬운 점
무엇이 더 중요한지는 작업마다 다르다. 개인정보 마스킹은 조금 더 가리더라도(정밀도 손해) 놓치지 않는 것(재현율)이 중요하다.
지금 · 실무에서
태그 학습을 했다면 CER과 별도로 '태그해야 할 구간 중 몇 %를 태그했나'를 평가셋에서 측정한다.

관련 그림: 개인정보 마스킹

합성 데이터

2010s~

Synthetic Data

시대적 배경
딥러닝이 대량의 정답 데이터를 요구하면서, 실제 데이터를 구하기 어렵거나 민감한 분야에서 프로그램으로 데이터를 만들어 쓰기 시작했다.
그래서 생긴 문제
개인정보가 들어간 실제 녹취는 학습에 쓰기 어렵고, 카드번호를 불러 주는 장면처럼 꼭 필요한 상황은 데이터에 드물다.
개념 · 역할
실제로 수집하지 않고 프로그램(규칙, TTS, 생성 모델)으로 만든 학습 데이터. 정답을 알고 만들기 때문에 라벨이 정확하다.
헷갈리기 쉬운 점
합성음만으로 학습하면 실제 통화의 잡음 · 말투 · 음질과 달라 현장 성능이 떨어진다. 반드시 실제 데이터와 섞는다.
지금 · 실무에서
개인정보 태그 학습에서 가상 카드번호 · 계좌 · 이름을 넣은 문장을 TTS로 합성하고, 8kHz 전화 음질로 변환해 쓴다.

관련 그림: 개인정보 마스킹

RAG (검색 증강 생성)

2020

Retrieval-Augmented Generation

시대적 배경
2020년 메타(페이스북) 연구진이 발표했다. 모델 안의 지식은 학습 시점에 멈추고, 회사 내부 문서는 아예 모른다.
그래서 생긴 문제
새 정보나 사내 문서를 알게 하려고 매번 파인튜닝하는 것은 비싸고, 효과도 불확실하며, 답의 근거를 보여 주지 못한다.
개념 · 역할
질문이 들어오면 관련 문서를 먼저 검색하고, 그 문서를 질문과 함께 LLM에 넣어 답을 생성하는 방식. 가중치를 바꾸지 않으므로 추론에 속한다.
헷갈리기 쉬운 점
검색이 엉뚱한 문서를 가져오면 답도 틀린다. 품질의 절반은 문서를 어떻게 나누고 검색하느냐에 달려 있다.
지금 · 실무에서
사내 문서 Q&A는 RAG, 말투 · 형식 · 특정 작업은 파인튜닝이 맞다. 둘을 함께 쓰기도 한다.
